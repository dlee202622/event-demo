02心智模型：一个 Java 进程的内存其实分四家

最常见的误解是「JVM 内存 = 堆 + 栈，-Xmx 就是上限」。这句话有三个漏洞，本文所有实验都在补这三刀。

误解版

  • 「-Xmx 设了 512 MB，进程最多用 512 MB」
  • 「OOM 就是堆不够，加 -Xmx 就行」
  • 「对象要熬满 15 次 Young GC 才进老年代」
  • 「String.intern() 会把字符串永久留在方法区，所以泄漏」

本文实测版

  • 观测进程 -Xmx=4096 MB，jcmd VM.native_memory 读出 committed=419466KB（约 410 MB），其中堆只占 200 MB
  • 六个 OOM 里三个炸在堆之外：Metaspace、StackOverflowError、Direct buffer memory
  • 本机 Serial 默认 new threshold 1：对象熬过一轮就晋升，15 只是上限
  • 20 万次 intern，一次 Full GC 后只剩 84 条；intern 案例两轮增长都是 0.00 MB
比

类比：一栋公寓楼 线程私有区是每户自己的鞋柜（人走了就拆）；堆是楼下的公共仓库，所有人往里堆东西，保洁（GC）定期清； 方法区是楼的管理处档案室（存放「这栋楼有哪些户型」的图纸，也就是类的元数据）； 直接内存是违建的地下一层——它不在物业管理范围里（不受 -Xmx 约束），但塌了照样埋整栋楼。

3.2 分配 → 丢弃引用 → 真正回收：三步分开

类比：仓库里的箱子。你「不再需要某个箱子」和「保洁把它拉走」是两件事，中间还隔着一趟保洁班车（GC）。 这一节把三件事拆成三次请求，每一步都刷新一次堆使用量。

java · area/HeapHolder.java：持有器只做一件事——决定要不要留强引用（节选）
public AllocationResult allocate(int megabytes, boolean retain) {
    if (megabytes > maxSingleMb) {                        // 默认上限 64 MB：打死观测进程就没有进程可看了
        throw new IllegalArgumentException("单次最多 " + maxSingleMb + " MB（demo.jvm.max-allocate-mb 可调），收到 " + megabytes + " MB");
    }
    if (Units.mbToBytes(megabytes) > freeHeapBytes()) {   // 先判断剩余空间：宁可返回 400 说明原因，也不要当场 OOM
        throw new IllegalArgumentException("堆剩余约 …，无法再分配 …，先调 /api/jvm/allocate/clear 释放");
    }
    byte[] block = new byte[(int) Units.mbToBytes(megabytes)];   // 真的 new，不预分配、不共享底层数组
    for (int i = 0; i < block.length; i += 4096) {
        block[i] = 1;                                     // 写一遍防止惰性分配：没写过的页可能还没占物理内存，指标会偏小
    }
    if (retain) {
        synchronized (retained) {                         // 保留 → 任何 GC 都收不走 → 老年代水位持续上涨
            retained.addLast(block);
            retainedBytes += block.length;
        }
    }                                                     // 不保留：方法返回后只剩栈上的局部引用，下次 Young GC 就收走
    return new AllocationResult(megabytes, retain, heldBlocks(), Units.mb(retainedBytes), /* 当前堆 used */);
}

04栈：一个参数、两笔账、一条直线（场景 2）

栈是初学者最容易「背过但没量过」的一格：-Xss 到底换来了多少递归深度？这一节把它拟合出来，顺便指出这条直线在什么地方会断。

4.1 -Xss 与递归深度：先拆成「固定开销 + 帧 × 深度」

类比：一条自动扶梯。你一次能多站多少人，不只取决于扶梯长度，还取决于入口那台机器占掉的固定格子数——把机器搬走是不可能的（每个线程都有），所以短扶梯的「人均占位」看起来大得多。

java · lab/StackDepthLab.java：一个刻意做小的帧，才能让「每帧字节数」有意义
/**
 * 单参数、单局部变量的最小帧：帧里只有 counter 引用加一个 int，
 * 这样「每帧字节数」才接近 HotSpot 的真实开销，不会被我顺手塞进帧的大数组污染。
 */
private static void recurse(int[] counter) {
    int frame = counter[0] + 1;   // 读改写而不是 counter[0]++：保证计数在溢出后仍能被 main 读到
    counter[0] = frame;
    if (frame >= HARD_LIMIT) {
        return;                   // 兜底：栈给得再大也不许无限递归，否则拟合点会带进一个「没溢出」的假数据
    }
    recurse(counter);             // 真正的递归：每调一次压一帧，帧大小就是要求的东西
}

算

模型能算出实测值 栈大小 = 每帧字节 × 深度 + 固定开销。代回去： (1024 × 1024 − 99904) ÷ 24 = 39527，实测 39528； (256 × 1024 − 99904) ÷ 24 = 6760，实测 6760。 两个尺寸的深度比是 39528 ÷ 6760 = 5.85，而栈只放大了 4 倍——多出来的就是那笔固定开销被摊薄了。

伪

fitR2=1.0 不代表模型被验证过，也不代表深度是个常数 两点必然拟合成一条完美直线，R²=1.0 在这里只说明「没算错」。拿第三个点去砸它才会露馅： 预热用的是 16 MB 栈，模型预测 (16777216 − 99904) ÷ 24 = 694888，实测 652599，少 6%—— 栈大到一定程度后，SOE 的来源不再是「帧放不下」。
更要命的是帧大小本身依赖 JIT 层级：lab.sh stack-depth（不带参数，跑 128~4096 KB 五档） 两次实测都是 main.depth=19766、frame.bytesFitted=48.08、fixedOverheadBytes=94828—— 帧正好是 24 B 的两倍，深度正好少一半。同一份代码、同一台机器，换个参数列表就换了编译档位。 结论：能当常数用的是「关系式」，不是「深度」。

4.2 局部变量表：帧里那一格到底多大，javap 说了算

这一节回答两个具体到能被编译器推翻的问题：long 参数占一槽还是两槽？同作用域外的两个局部变量会不会共用一槽？

java · lab/LocalSlotSample.java：两个样本方法刻意做出「复用槽」和「压住活引用」
/** 期望 locals=2：first 与 second 各自只在一个分支里活着，生命周期不重叠 → 共用 1 号槽。 */
public static int reusesSlotsInSequentialBlocks(boolean flag) {
    if (flag) {
        int first = 1;      // 作用域到 return 就结束了；槽号 1，有效区间从字节码 6 起、长 2
        return first;
    }
    int second = 2;         // 同样是槽 1，但有效区间从字节码 10 起 —— 与 first 不重叠，才敢复用
    return second;
}

/** 期望 locals=4：a、b、c 声明位置一样，但 return 要把三个都读一遍 → 谁也不能复用谁。 */
public static int keepsLocalsAlive(int seed) {
    int a = seed + 1;
    int b = seed + 2;       // 到这一步 a 仍然可能被后面读到，不能释放
    int c = a + b;          // 同时读 a 和 b：三个变量生命周期重叠，只能各占一槽
    return a + b + c;       // 这一行让 a、b 的存活区间一直拉到方法末尾
}

7.2 回收后的水位为什么一路上涨

把上面六行的第二个数字连起来看：15 → 24 → 30 → 38 → 48 → 59 MB。每行都是「这次 GC 结束后」的堆使用量，而负载里常驻对象只有 live=8 MB。

  • 涨的不是垃圾，是晋升：动态阈值被挤成 1（第 8.1 节），每轮 Young GC 都往老年代搬一批，而 Serial 的老年代只在全停时才清。
  • 所以 gc.usedEndMb=44.76 对 heap.xmxMb=123.75 的走向是「老年代单调上升」， Serial 单收集器实测 gc.countInProcess=20 里就包含 Full GC（MarkSweepCompact）。
  • 同一份负载在 G1 上 peakMB=189、ZGC 上 peakMB=256：并发收集器允许堆「用水位换停顿」， 这是设计，不是配坏了。判断标准是 stall 而不是 peakMB。
缺

只写 -Xlog:gc* 拿不到对象年龄表 年龄分布属于 gc+age 子标签的 debug/trace 级别，第 8 章的实验旗标是 "-Xlog:gc*,gc+age=trace"。少了 gc+age=trace，日志里就没有 - age N: 这些行， 你会以为「对象没有变老」——实际上只是没打印。

8.2 怎么让对象真的变老

  2. 把常驻集变小：本实验 live=8 MB 相对 64 MB 堆太大；真实应用要看 -Xmx 与存活集比例，不是看参数表里别人写多少。

09内存泄漏取证：三种常见姿势、一套命令链（场景 6）

  • 真正留在原生内存里的是桶数组：泄漏版 1.00 MB、修好版 0.50 MB。这笔账在 jcmd GC.class_histogram 里完全看不到——它只统计堆里的 Java 对象，不统计 JVM 内部的_NATIVE_ 结构。
