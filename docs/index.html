DDD 事件驱动 Demo

以「订单」限界上下文为主线，把领域建模、领域事件、CQRS 读模型与 Outbox 可靠投递串成一条可运行、可验证的完整链路。 不依赖任何外部中间件，启动即用；每一层都留好了替换成 MySQL、Kafka、RocketMQ 的接缝。

Java 21 Spring Boot 4.1.2 零 外部中间件 7 个测试通过 12 个 HTTP 接口

1 · 项目概览

这不是一个只展示注解的脚手架，而是一份「边界清晰」的最小可运行示例。四个能力点各自独立，又能串成一条链路： 下单写聚合、聚合发事件、事件驱动下游、下游投影读模型、Outbox 把事件送到 MQ。

聚合自守

状态流转与不变量写在 Order 内部，外部拿不到 setter，规则无法被绕过。

事件解耦

订单不感知库存、积分、通知。新增一个下游只需加订阅者，用例代码零改动。

读写分离

查询走 OrderView 读模型，不为展示一个列表而重建整个聚合。

可靠投递

Outbox 表 + 定时中继 + 消费端 eventId 幂等，扛住至少一次语义。

一次下单请求发生了什么

写模型
Order.place() 校验并创建聚合，登记 OrderCreatedEvent，但此刻还没有发出去。
持久化
应用服务先 save(order)，保证读侧能查到数据，再拉取并发布事件。
扇出
事件被 4 类订阅者消费：库存预占、读模型投影、通知、Outbox 发件箱。
投递
Outbox 中继定时把事件发到 topic=order-events，消息 key 使用 orderId 保证同聚合有序。

4 · 事件流

聚合只负责「登记」事件，应用服务在保存之后统一「发布」，发布器再写事件存储并交给 Spring 的事件多播器。 订阅者之间互不感知，谁订阅了什么，只有订阅者自己知道。

事件清单

领域事件触发时机订阅者关键载荷
OrderCreatedEventOrder.place() 库存预占、读模型、通知、Outbox orderId、customerId、totalAmount、items 快照
OrderConfirmedEventconfirm() 读模型、通知、Outbox orderId、occurredOn
OrderPaidEventpay(paymentId) 积分发放、读模型、通知、Outbox orderId、customerId、paidAmount、paymentId
OrderCancelledEventcancel(reason) 库存释放、读模型、通知、Outbox orderId、reason、items 快照
为什么取消事件要带 items？库存上下文释放占用时需要商品明细。如果只给 orderId， 它就必须反向调用订单服务查询——那已经退化成伪装成事件的 RPC。事件必须自解释， 这也是「事件驱动」和「消息通知」的分水岭。

5 · 核心实现

5.1 聚合根基类：先登记，后发布

聚合在业务方法里只登记事件，不接触任何事件总线。发布时机交给应用层，这样领域层保持纯净， 也不会出现「事件已经发出去、数据却写失败」的错序。

shared/domain/AggregateRoot.javajava
public abstract class AggregateRoot {

    private final transient List<DomainEvent> domainEvents = new ArrayList<>();

    protected void registerEvent(DomainEvent event) {
        this.domainEvents.add(event);
    }

    public List<DomainEvent> pullDomainEvents() {
        List<DomainEvent> events = List.copyOf(this.domainEvents);
        this.domainEvents.clear();          // 拉取即清空，天然防重复投递
        return events;
    }
}

5.2 聚合根：创建即合法

工厂方法把「金额 = 各行小计之和」「至少一个商品」「客户不能为空」这些不变量一次性守住， 外部无法构造出半个不合法的订单。

order/domain/model/Order.javajava
public static Order place(OrderId id, String customerId, List<OrderItem> items) {
    if (customerId == null || customerId.isBlank()) {
        throw new DomainException("客户 ID 不能为空");
    }
    if (items == null || items.isEmpty()) {
        throw new DomainException("订单至少需要包含一个商品");
    }
    Money total = items.stream()
            .map(OrderItem::subtotal)
            .reduce(Money.ZERO, Money::add);

    Instant now = Instant.now();
    Order order = new Order(id, customerId, items, OrderStatus.CREATED, total, null, now, now);

    order.registerEvent(new OrderCreatedEvent(
            UUID.randomUUID().toString(), id.value(), customerId, total, order.items, now));
    return order;
}

5.3 应用服务：四步用例

加载或创建聚合 → 调用业务方法 → 保存 → 发布事件。所有用例都只有这几行，业务规则不在这里。

order/application/OrderApplicationService.javajava
public OrderId placeOrder(PlaceOrderCommand command) {
    List<OrderItem> items = command.lines().stream()
            .map(line -> new OrderItem(line.productId(), line.productName(),
                    new Money(line.unitPrice(), Money.CNY), line.quantity()))
            .toList();

    Order order = Order.place(orderRepository.nextId(), command.customerId(), items);

    orderRepository.save(order);      // 1. 先落库
    publishEvents(order);             // 2. 再发事件

    log.info("[应用服务] 下单成功 orderId={} 金额={}",
            order.id().value(), order.totalAmount().display());
    return order.id();
}

5.4 消费端：幂等是硬要求

事件驱动默认为「至少一次」语义，重试、重投、重启都会造成重复消费。 每个订阅者都必须用 eventId 做去重，越靠前的检查越好。

loyalty/event/LoyaltyEventListener.javajava
@EventListener
public void on(OrderPaidEvent event) {
    if (!processedEventRegistry.markIfAbsent(event.eventId())) {
        log.warn("[积分上下文] 重复事件已跳过 eventId={}", event.eventId());
        return;
    }

    int earned = event.paidAmount().amount()
            .divide(BigDecimal.TEN, 0, RoundingMode.DOWN)
            .intValue();

    int total = loyaltyPointsService.earn(event.customerId(), earned);
    log.info("[积分上下文] 客户 {} 本次 +{} 积分，累计 {}",
            event.customerId(), earned, total);
}

5.5 Outbox 中继：把事件可靠地送出去

「业务数据落库」和「事件投递到 MQ」无法在同一个本地事务里完成。做法是先把事件写进 outbox 表 （与业务写入同事务），再由独立线程轮询投递，投递成功才标记。

shared/infrastructure/outbox/OutboxRelay.javajava
@Scheduled(fixedDelayString = "${demo.outbox.relay-interval-ms:3000}", initialDelay = 2000)
public void relay() {
    if (!relayEnabled) return;
    flush();
}

public synchronized int flush() {
    List<OutboxEvent> batch = outboxStore.claimPending(properties.getOutbox().getClaimBatchSize());
    if (batch.isEmpty()) return 0;

    for (OutboxEvent event : batch) {
        rabbitTemplate.convertAndSend(exchange, routingKey, message);
        outboxStore.markDelivered(event.id());
    }
    log.info("[Outbox→RabbitMQ] 本轮认领 {} 条、发送成功 {} 条", batch.size(), sent);
    return sent;
}
三个容易被忽略的细节：消息 key 用 aggregateId，同一订单的事件落到同一分区，顺序有保证； 多实例部署时用 SELECT ... FOR UPDATE SKIP LOCKED 抢占待投递记录，避免重复投递； 设置最大重试次数并落死信表，防止单条毒消息阻塞整个中继。

7 · 设计决策与生产建议

关注点本项目的做法生产建议
事件何时发布 聚合内登记，保存聚合之后统一发布 业务写入与 outbox 写入放到同一本地事务
领域层是否依赖框架 否，Order 只依赖 AggregateRoot 与 DomainException 保持纯净，领域层可单测、可迁移
事件与数据的原子性 OutboxStore 模拟 outbox 表，中继轮询投递 outbox 表 + SKIP LOCKED 抢占，或 CDC（Debezium）
重复投递 ProcessedEventRegistry 按 eventId 去重 Redis SETNX + TTL，或唯一索引（event_id, consumer_group）
事件顺序 内存按写入顺序，投递 key 用 aggregateId Kafka 分区 key = aggregateId，同聚合严格有序
读写分离 OrderView 由投影维护，查询不加载聚合 读模型落 ES / 只读库，独立扩容
读模型重建 清空后按事件流重放（rebuild()） 投影版本化 + 影子表切换，避免重建期不可用
跨上下文耦合 只共享事件契约，不共享聚合与仓储 事件字段只增不删，语义向后兼容
失败补偿 库存不足仅告警（示例简化） 发布 StockReservationFailedEvent 驱动订单取消（Saga）

9 · 接入真实中间件

从内存实现切到 Kafka / RocketMQ 只需要四步，领域层与应用层代码一行都不用改。

  1. 在 pom.xml 中加入 spring-kafka 或 rocketmq-spring-boot-starter。
  2. 把 OutboxRelay.flush() 里的日志替换为 kafkaTemplate.send(topic, aggregateId, payload)，成功回调中标记已投递，失败进入重试与死信。
  3. 下游把 @EventListener 换成 @KafkaListener(topics = "order-events")，幂等与业务逻辑原样复用。
  4. 需要跨实例事务一致性时，把内存 Store 换成 MySQL/JPA，用 @Transactional 包住「业务写入 + outbox 写入」。
application.yaml（生产者示例，当前为注释状态）yaml
spring:
  kafka:
    bootstrap-servers: localhost:9092
    producer:
      acks: all
      enable-idempotence: true
      key-serializer: org.apache.kafka.common.serialization.StringSerializer
      value-serializer: org.apache.kafka.common.serialization.StringSerializer
上线前请确认三件事：消费者是否都做了幂等；消息 key 是否用了聚合 ID；Outbox 是否有重试上限和死信兜底。 这三条决定了链路在故障时是「自愈」还是「雪崩」。
