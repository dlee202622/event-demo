1心智模型：一条 SQL 的旅程

最常见的误解是「MySQL = 磁盘上的表」。 真相是：任何读写都要先经过内存里的 Buffer Pool，磁盘只是它的后备仓库。

三个立刻能用的推论，后面每章都会反复出现：

  1. IO 的最小单位是页，不是行。 读一行 = 读一页（16KB），所以「让一页里少装没用的数据」「让相关的行挨在一起」直接决定性能。
  2. 提交很快，是因为它只写 redo log（顺序 IO），不刷数据页（随机 IO）。 这是第 5 章的主题。
  3. 读得快，是因为页在内存。 第 2 章会看到：同样的数据，不同的主键设计会让页数差 20%。

2数据结构：页与 B+ 树

InnoDB 管理数据的最小单位是页（page）：固定 16KB。 一棵存数据的 B+ 树，树干是「索引页」，树叶是「数据页」——树本身就是索引，这个设计贯穿全文。

2.1 为什么偏偏是 B+ 树

给「按主键 O(log N) 找到一行、还要支持范围扫描」这个需求，候选数据结构有四个，逐一淘汰：

候选结构等值查询范围查询被淘汰的原因
哈希表O(1)，很快不行，键无序业务里 WHERE id BETWEEN、ORDER BY 太常见；Memory 引擎才默认用它
二叉/红黑树O(log N)可以二叉扇出 = 树高 = log₂N：2000 万行高约 25 层，就是 25 次页 IO
B 树O(log N)可以但要中序回溯每个节点都存整行 → 单节点放不了几个键 → 扇出小树变高；范围查询要在树上爬上爬下
B+ 树O(log N)叶子链表直出——入选：扇出上千 → 3 层装 2000 万行；叶子成链 → BETWEEN/LIMIT 顺链走
答

面试高频题的标准答案就一句话：B+ 树把「扇出」做到了上千（内节点不存数据）， 让树高压到 3 层以内（3 次页 IO），同时叶子层双向链表让范围查询变成顺链遍历。 哈希赢在单点、输在范围；二叉树输在树高；B 树输在节点密度和范围回溯。

2.2 实测：页分裂 —— 递增主键 vs UUID 主键

往有序的叶子链表里插数据有两种姿势：

下面实测。建两张结构相同的表，各插 30 万行、行宽约 150 字节： 一张主键自增（按序到达），一张主键是 MD5 字符串（随机到达）， 对比插入耗时和文件大小。完整脚本见 docs/mysql-guide-labs/exp1-pagesplit.sql。

exp1-pagesplit.sql（节选）
-- 表 1：递增主键，数据按主键升序到达
CREATE TABLE inc_pk (
  id      BIGINT       NOT NULL,
  name    VARCHAR(32)  NOT NULL,
  padding VARCHAR(128) NOT NULL,        -- 撑宽行，让每页能装几行变得可观察
  PRIMARY KEY (id)
) ENGINE=InnoDB;

SET @t = NOW(6);                          -- 记录起点（微秒精度）
INSERT INTO inc_pk
SELECT n, CONCAT('user-', n), RPAD('p', 128, 'x')
FROM nums WHERE n <= 300000 ORDER BY n;   -- 30 万行按主键升序插入
SELECT TIMESTAMPDIFF(MICROSECOND, @t, NOW(6))/1e6 AS inc_insert_sec;

-- 表 2：UUID 主键（MD5 模拟），数据按随机顺序到达
CREATE TABLE uuid_pk (
  id      CHAR(32)     NOT NULL,          -- MD5：下一个键落点完全随机
  src     BIGINT       NOT NULL,
  name    VARCHAR(32)  NOT NULL,
  padding VARCHAR(128) NOT NULL,
  PRIMARY KEY (id)
) ENGINE=InnoDB;

SET @t = NOW(6);
INSERT INTO uuid_pk
SELECT MD5(n), n, CONCAT('user-', n), RPAD('p', 128, 'x')
FROM nums WHERE n <= 300000 ORDER BY MD5(n);  -- 关键：按 MD5 排序 = 随机到达
SELECT TIMESTAMPDIFF(MICROSECOND, @t, NOW(6))/1e6 AS uuid_insert_sec;

-- 结构对比：.ibd 文件大小 + 统计信息
SELECT NAME, FILE_SIZE/1024/1024 AS file_mb
FROM information_schema.INNODB_TABLESPACES
WHERE NAME LIKE 'demo_mysql_principle/%pk';
ANALYZE TABLE inc_pk, uuid_pk;            -- 刷新行数/平均行长统计

主键尽量自增（AUTO_INCREMENT / 雪花 ID），别用 UUID、别用随机业务键。 32 位 UUID 作为主键还会让所有二级索引跟着膨胀——每个二级索引叶子都存主键值（见 3.1）。 实在要用分布式 ID，选趋势递增的方案（雪花算法）。

3索引：回表、覆盖与最左前缀

InnoDB 里只有两类索引：聚簇索引（叶子=整行）和二级索引（叶子=索引列+主键）。 理解这句话，回表、覆盖、最左前缀全是推论。

3.2 实测：覆盖索引到底省了什么

用 emp 表（30 万行，bio 字段 600 字节，部门 100 个）做实验： 同样是 WHERE dept_id = 7（命中 3005 行），一条查询取整行（必须回表）， 一条只算二级索引里已有的列（覆盖）。完整脚本见 docs/mysql-guide-labs/exp2c-cover.sql。

exp2c-cover.sql（节选）
-- 路径 A（回表）：SUM(LENGTH(bio)) 必须读整行 → 3005 次回聚簇索引
FLUSH STATUS;                             -- 把会话计数器清零，隔离本次查询
SELECT SUM(LENGTH(bio)) AS total_bio_len FROM emp WHERE dept_id = 7;
SHOW SESSION STATUS LIKE 'Innodb_buffer_pool_read_requests';  -- 逻辑读次数

-- 路径 B（覆盖）：SUM(id) + SUM(dept_id) 只用二级索引 → 零回表
FLUSH STATUS;
SELECT SUM(id) + SUM(dept_id) AS cover_sum FROM emp WHERE dept_id = 7;
SHOW SESSION STATUS LIKE 'Innodb_buffer_pool_read_requests';

-- 用 EXPLAIN 看结构性证据：Extra 列
EXPLAIN SELECT SUM(LENGTH(bio))    FROM emp WHERE dept_id = 7;  -- Extra: NULL
EXPLAIN SELECT SUM(id) + SUM(dept_id) FROM emp WHERE dept_id = 7; -- Extra: Using index

3.3 实测：最左前缀 —— 联合索引是「排好序的电话本」

联合索引 idx_abc(a, b, c) 的排序规则和字典一样：先按 a 排，a 相同按 b 排，b 相同按 c 排。 所以「跳过 a 直接查 b」就像在字典里按第二个字找词——只能整本翻。

最左前缀六连（exp2-index.sql 节选）
CREATE TABLE idx_abc (
  a INT NOT NULL, b INT NOT NULL, c INT NOT NULL, d VARCHAR(16) NOT NULL,
  KEY idx_abc (a, b, c)              -- 列都是 NOT NULL，key_len 干净：a=4B, b=4B, c=4B
) ENGINE=InnoDB;
-- 插入 20 万行后 ANALYZE，然后依次执行：

EXPLAIN SELECT * FROM idx_abc WHERE a = 5;
EXPLAIN SELECT * FROM idx_abc WHERE a = 5 AND b = 50;
EXPLAIN SELECT * FROM idx_abc WHERE a = 5 AND b = 50 AND c = 500;
EXPLAIN SELECT * FROM idx_abc WHERE b = 50;              -- 跳过 a
EXPLAIN SELECT * FROM idx_abc WHERE c = 500;             -- 跳过 a、b
EXPLAIN SELECT * FROM idx_abc WHERE a = 5 AND c = 500;   -- 中间断层：只有 a 生效

key_len 是「索引被用了几成」的仪表盘：INT 每列 4 字节， key_len=8 说明 a、b 都参与定位，=12 说明三列全用。中间断层（a=? AND c=?） 时 c 退化为 ICP（Index Condition Pushdown，索引条件下推）：仍会在索引层过滤， 但帮不上「定位缩小范围」。

列上明明有索引，优化器却弃用，最常见就四种姿势。都在 emp（30 万行）上实测：

EXPLAIN SELECT * FROM emp WHERE phone = '13812345678';   -- 1) 基准：字符串等值

4事务与 MVCC

两个事务一个在读、一个在写同一行，互不阻塞还能互不看到对方的中间状态—— 靠的不是锁，而是 MVCC（Multi-Version Concurrency Control，多版本并发控制）：每行数据留一条版本链，读的人按自己的「快照」挑版本。

4.1 隔离级别与版本链

隔离级别脏读不可重复读幻读实现
READ UNCOMMITTED有有有直接读最新值，几乎没人用
READ COMMITTED（RC）无有有每条 SELECT 都生成新快照
REPEATABLE-READ（默认）无无基本无*事务内第一条快照读生成快照，全程复用
SERIALIZABLE无无无读也加锁，并发退化为串行

* InnoDB 的 RR 通过临键锁（6.1）把常见幻读场景也挡住了，这是它区别于 SQL 标准的地方。

读

快照读 vs 当前读，是本章最容易踩的坑：

普通 SELECT 是快照读——走版本链，不加锁； SELECT … FOR UPDATE、UPDATE、DELETE 是当前读——读最新已提交版本，必须拿锁。 同一个事务里，快照读可能读到旧值，紧接着的当前读却能看到新值（下面的实测正好演示了这一点）。

4.2 实测：RR 看到旧值，RC 看到新值

两个会话并发：会话 A 开事务读一行后停 4 秒，会话 B 在第 1 秒把这行改成 v=2 并提交。 脚本见 docs/mysql-guide-labs/run-mvcc.sh（自动编排双会话时序）。

sessA-rr.sql（会话 A · REPEATABLE-READ）
-- 会话 A 全程：t0 拍快照 → 等 B 提交 → 快照读/当前读对比 → 提交后新快照
SET SESSION transaction_isolation = 'REPEATABLE-READ';
BEGIN;                                              -- 开事务
SELECT v, note FROM mvcc_demo WHERE id = 1;         -- t0：第一次快照读，此刻拍快照
SELECT SLEEP(4);                                    -- 停 4 秒，等 B 提交
SELECT v, note FROM mvcc_demo WHERE id = 1;         -- t1：再读一次（快照读）
SELECT v, note FROM mvcc_demo WHERE id = 1 FOR UPDATE;  -- t2：当前读，读最新已提交
COMMIT;

5.3 实测：innodb_flush_log_at_trx_commit = 1 vs 2

这个参数控制「提交时 redo log 刷不刷盘」：=1 每次提交都 fsync（默认，最安全）； =2 只写到操作系统的页缓存，由 OS 每秒落盘（进程崩溃不丢，机器断电丢最后 1 秒）。 各以「单行独立事务」提交 5000 次（完整脚本见 docs/mysql-guide-labs/exp3-flush-bp.sql）：

exp3-flush-bp.sql（节选）
DROP PROCEDURE IF EXISTS burn_writes;
DELIMITER //
CREATE PROCEDURE burn_writes(IN n INT)
BEGIN
  DECLARE i INT DEFAULT 0;
  SET @t = NOW(6);
  WHILE i < n DO
    INSERT INTO flush_t (v) VALUES (i);   -- autocommit=1：每条 INSERT 都是独立提交
    SET i = i + 1;
  END WHILE;
  SELECT TIMESTAMPDIFF(MICROSECOND, @t, NOW(6))/1e6 AS burn_sec, n AS commits;
END//
DELIMITER ;

SET GLOBAL innodb_flush_log_at_trx_commit = 2;   -- 先测不刷盘
CALL burn_writes(5000);
TRUNCATE TABLE flush_t;
SET GLOBAL innodb_flush_log_at_trx_commit = 1;   -- 再测每次 fsync（默认值）
CALL burn_writes(5000);

本机（Docker Desktop on macOS）fsync 便宜，差距只有 12%；别把数字当普适结论。 生产环境一次 fsync 0.5~2ms（云盘更贵），叠加 sync_binlog=1 的 binlog 刷盘后， =1 与 =2 的差距常达 2~5 倍——所以大促前有人敢把 =1 调成 =2 换吞吐， 但要清楚这是用「断电丢 1 秒」换性能，金融类业务别碰。

6锁与死锁

MVCC 管「读不阻塞读」，锁管「写与写的秩序」。InnoDB 的行锁有三种粒度， 它们加锁的对象都不是「行」，而是「记录 + 它前面的间隙」。

6.2 实测：死锁复现与自动解救

经典互锁：A 先锁 id=1 再要 id=2，B 先锁 id=2 再要 id=1。脚本见 docs/mysql-guide-labs/run-locks.sh（编排两个会话的时序）。

sessA-dl.sql / sessB-dl.sql（会话 A 与 B）
-- 会话 A                                -- 会话 B
BEGIN;                                   BEGIN;
UPDATE deadlock_demo SET v=v+1           UPDATE deadlock_demo SET v=v+1
  WHERE id = 1;      -- A 拿到 1           WHERE id = 2;      -- B 拿到 2
SELECT SLEEP(2);                         SELECT SLEEP(2.5);
UPDATE deadlock_demo SET v=v+1           UPDATE deadlock_demo SET v=v+1
  WHERE id = 2;      -- 等 B 放 2 …        WHERE id = 1;      -- 等 A 放 1 → 死锁！
COMMIT;                                  ROLLBACK;

死锁不是故障，是 InnoDB 的正常保护机制：检测到环路立刻回滚代价小的事务（错误码 1213）， 应用收到后重试即可。预防思路只有一条：让所有事务按相同顺序拿锁（比如都按 id 升序更新）， 环路就不存在。另一类「锁等待超时」是 ERROR 1205——那是没成环，单纯等太久（默认 50 秒）。

6.3 实测：间隙锁阻塞插入

会话 A 对 [5,15] 做范围当前读（FOR UPDATE），持有 3 秒； 会话 B 第 1 秒尝试插入 id=7——落在 (5,10) 的间隙里：

sessA-gap.sql / sessB-gap.sql
-- 会话 A                                -- 会话 B
BEGIN;                                   SET SESSION innodb_lock_wait_timeout = 20;
SELECT id, note FROM gap_demo            SET @t = NOW(6);
  WHERE id BETWEEN 5 AND 15              INSERT INTO gap_demo VALUES (7, '…');
  FOR UPDATE;   -- 临键锁 (5,10]…         -- 阻塞中 … 直到 A 提交
SELECT SLEEP(3); COMMIT;                 SELECT TIMESTAMPDIFF(MICROSECOND,@t,NOW(6))/1e6
                                            AS insert_waited_sec;  -- 实际等了多久

|  5 | r5   |

+----+------+

| tag                  | insert_waited_sec |
+----------------------+-------------------+

范围当前读会锁住整段间隙，等于冻结这段区间的所有写入。 业务里最常见的踩法：对「不存在的记录」先 SELECT … FOR UPDATE 判断再 INSERT（防重逻辑）， 在 RR 下并发插入会被间隙锁连环阻塞甚至死锁。防重复请用唯一索引 + INSERT … ON DUPLICATE KEY， 锁冲突粒度从「区间」缩小到「一个键」。

7.1 实测：深分页 —— LIMIT 900000, 10 的真实成本

LIMIT 900000, 10 的语义是：老老实实扫过前 90 万行、丢弃、再取 10 行。 100 万行的 orders_big 表上实测三种写法（各跑 5 次取平均， 脚本在 docs/mysql-guide-labs/exp2-index.sql 的 time_page 过程）：

深分页三种写法
-- 写法 1：直接翻页（反例）
SELECT * FROM orders_big ORDER BY id LIMIT 900000, 10;

-- 写法 2：游标 / keyset 分页 —— 记住上一页最后的 id
SELECT * FROM orders_big WHERE id > 900000 ORDER BY id LIMIT 10;

-- 写法 3：延迟关联 —— 子查询先用覆盖索引把 10 个 id 挑出来再取整行
SELECT o.* FROM orders_big o
JOIN (SELECT id FROM orders_big ORDER BY id LIMIT 900000, 10) t ON o.id = t.id;
