01心智模型：Redis 是「数据结构的服务器」

很多人把 Redis 记成一堆命令，于是总在「这个场景该用哪个命令」上卡住。 更省力的记法是：先想数据长什么形状，形状对了，命令自然就出来了。

把 Redis 想成一个巨大的药柜：每个抽屉有一个名字（key）， 抽屉里放的不是随便一坨字节，而是九种标准容器之一（value）。 SET 是往抽屉里放一张纸条，HSET 是放一个带格子的药盒， ZADD 是放一个会自动按分数排序的文件夹。

单线程执行命令

Redis 用一个线程按顺序执行命令（网络读写可以多线程）。 所以单条命令天然原子，不需要你加锁；但也意味着一条慢命令会堵住所有人。

Lua 是「原子事务」

需要「先判断再写入」时，把逻辑写成 Lua。脚本执行期间不会插入其他命令， 限流和锁都靠这一点保证正确性。

内存 + 持久化

数据主要在内存，RDB 做快照、AOF 记命令日志。 重启能不能恢复、丢多少，取决于持久化配置，不是「Redis 一定不丢」。

先问三个问题，再选类型

  1. 你要按 key 取整块值，还是要操作其中一部分？ 整块用 String，字段级用 Hash。
  2. 顺序重要吗？ 要排队/时间线用 List，要按分数排名用 ZSet。
  3. 是集合运算还是布尔标记？ 去重/交并用 Set，大规模 0/1 状态用 Bitmap。
✓

命名空间是给自己留的后路 本仓库统一用 demo:types:zset:leaderboard 这种冒号分隔的 key。 生产里至少带上「业务:对象:ID」，否则 KEYS * 和清理脚本会变成灾难。

02九种数据类型：先看形状，再记命令

九种类型并不是九个孤立的知识点。它们覆盖了四种基本形状： 单值、字段集合、有序集合、以及「用位/概率压缩的集合」。

类型一句话典型场景别拿它做
String一个 key 一个值对象缓存、计数器、SETNX 占位存超大 JSON（会阻塞单线程）
Hash一个 key 多个字段用户资料、购物车、配置字段极多还频繁 HGETALL
List链表，两端进出队列、栈、最新 N 条需要 ACK/重投的消息队列
Set无序去重集合标签、共同好友、抽奖去重需要按分数排序
ZSet带分数的有序集合排行榜、延迟队列、权重队列纯去重（用 Set 更省）
Bitmap按位标记的 String签到、在线状态、布尔统计偏移量无界（会浪费内存）
HyperLogLog估算基数UV、独立访客需要精确值或原始元素
Geo经纬度 + 半径查询附近的人/店高精度轨迹计算
Stream消息流 + 消费者组轻量消息队列、事件流超大规模消息中间件替代品

String：最普通，也最常被低估

String 是一个抽屉里放一张纸条：整张读、整张写。三种高频用法是 对象缓存、原子计数、SETNX 占位。

Redis 命令
# 整块写、整块读
SET  demo:types:string:user:1:name 张三          # → OK，读回 "张三"

# 原子计数：INCR 不会丢更新，因为单条命令由 Redis 串行执行
INCR demo:types:string:article:1001:views        # → 1
INCRBY demo:types:string:article:1001:views 9    # → 10

# SETNX：key 不存在才写入，用来做「占位」
SETNX demo:types:string:lock:order:1 instance-A  # → 1（第一次成功）
SETNX demo:types:string:lock:order:1 instance-B  # → 0（第二次失败）
demo-redis/.../types/DataTypeService.java
// 整块写入一个字符串值
redis.opsForValue().set(nameKey, "张三");

// 原子自增：返回自增后的值，两行分别得到 1、10
Long views = redis.opsForValue().increment(viewsKey);
views = redis.opsForValue().increment(viewsKey, 9);

// SETNX 语义：key 已存在时返回 false，不会覆盖
Boolean first = redis.opsForValue().setIfAbsent(lockKey, "instance-A");
Boolean second = redis.opsForValue().setIfAbsent(lockKey, "instance-B");
// first=true, second=false
!

SETNX 只是锁的起点 它没有过期时间，也没有「只删自己的锁」的校验。进程崩溃后锁就永远在了。 正确的锁在 第 4 节，由 SET NX PX + Lua 组成。

Hash：只改一个字段，不用搬整个对象

把用户资料存成 JSON 时，改城市要先读出来、改完再写回去。 Hash 把对象拆成字段，HSET user city 杭州 只动一个格子。

Redis 命令
# 一次写入三个字段，返回新增字段数 3
HSET demo:types:hash:user:1001 name 张三 age 28 city 上海

# 只改 city，其他字段原样保留，返回 0 表示是覆盖而非新增
HSET demo:types:hash:user:1001 city 杭州

# 字段级原子自增，返回 29
HINCRBY demo:types:hash:user:1001 age 1

适用：字段较多、每次只改少数字段。注意字段特别多时不要频繁 HGETALL， 用 HMGET 按需取。小 Hash 在 Redis 内部用 listpack 紧凑存储。

List：两端进出的链表

把 List 想成一列火车：LPUSH 从车头挂车厢，RPUSH 从车尾挂。 左边进右边出是队列，同一边进出就是栈。

Redis 命令
RPUSH demo:types:list:task:queue task-1 task-2 task-3
# → [task-1, task-2, task-3]
LPUSH demo:types:list:task:queue task-0
# → [task-0, task-1, task-2, task-3]
RPOP  demo:types:list:task:queue
# → task-3，剩余 3 个
!

List 不是可靠队列 BRPOP 取走消息后进程崩溃，消息就丢了，没有 ACK 和重投。 需要这些能力时用 Stream（本节最后一个案例）。

Set：去重和交并差

Set 像一袋不重复的弹珠。共同好友就是 SINTER，推荐候选就是 SUNION， 运算在 Redis 内部完成，不用把整袋弹珠倒到应用里。

Redis 命令
# 两个用户的标签集合
SADD demo:types:set:user:1:tags 篮球 音乐 编程
SADD demo:types:set:user:2:tags 音乐 旅行

# 交集：共同标签 → [音乐]
SINTER demo:types:set:user:1:tags demo:types:set:user:2:tags

# 并集：去重后合并 → 篮球、音乐、编程、旅行
SUNION demo:types:set:user:1:tags demo:types:set:user:2:tags

大集合的交集复杂度与元素数相关。抽奖去重、共同关注、黑名单都常用 Set。

ZSet：会自己排序的集合

ZSet 给每个成员挂一个分数（score），查询时按分数排序。 排行榜只是它的一半用途，另一半是延迟队列： 把 score 写成「到期时间戳」，轮询 score ≤ now 的成员即可。

Redis 命令
# 写入三名玩家：分数在前，成员在后
ZADD demo:types:zset:leaderboard 100 张三 80 李四 60 王五

# 给李四加 30 分，返回新分数 110（原子操作）
ZINCRBY demo:types:zset:leaderboard 30 李四

# 按分数从高到低取前两名 → 李四 110，张三 100
ZREVRANGE demo:types:zset:leaderboard 0 1 WITHSCORES

# 延迟任务：score 存到期毫秒时间戳，轮询 ZRANGEBYSCORE 0 now
ZADD demo:types:zset:delay 1793188597088 order-1001
demo-redis/.../types/DataTypeService.java
// 写入成员与分数
redis.opsForZSet().add(key, "张三", 100);

// 给李四加 30 分，返回 110.0
Double score = redis.opsForZSet().incrementScore(key, "李四", 30);

// 按分数倒序取前两名，TypedTuple 同时带 member 和 score
Set<ZSetOperations.TypedTuple<String>> top =
        redis.opsForZSet().reverseRangeWithScores(key, 0, 1);

底层是跳表 + 哈希：按分数范围查、取排名都是 O(logN)。 相同 score 的成员按字典序排列，这个细节在分页时会影响稳定性。

Bitmap：用位来记「有 / 没有」

Bitmap 本质是 String，但按位读写。一个用户一个月的签到只需要 31 个 bit（4 字节）， BITCOUNT 直接得到签到天数。在线状态同理：用户 ID 当偏移量。

Redis 命令
SETBIT demo:types:bitmap:sign:user:1:2026-10 0 1   # 第 1 天
SETBIT demo:types:bitmap:sign:user:1:2026-10 1 1   # 第 2 天
SETBIT demo:types:bitmap:sign:user:1:2026-10 3 1   # 第 4 天
SETBIT demo:types:bitmap:sign:user:1:2026-10 7 1   # 第 8 天
SETBIT demo:types:bitmap:sign:user:1:2026-10 15 1  # 第 16 天
BITCOUNT demo:types:bitmap:sign:user:1:2026-10     # → 5
GETBIT   demo:types:bitmap:sign:user:1:2026-10 2   # → 0（第 3 天没签到）
!

偏移量必须可控 如果用用户 ID 当偏移量，而 ID 是雪花算法生成的长整型，Bitmap 会被撑到极大。 这种场景要先把 ID 映射到连续的小编号，或者换 Set。

HyperLogLog：用 12KB 估算千万 UV

统计 UV 时，精确去重需要把每个用户都存下来。HyperLogLog 只维护一个概率结构， 无论多少元素都占约 12KB，标准误差 0.81%。代价是：只给估算值，拿不回原始元素。

Redis 命令
PFADD demo:types:hll:uv:2026-10-28 u1 u2 u3 u2   # → 3（u2 重复）
PFADD demo:types:hll:uv:2026-10-28 u4 u5         # → 5
PFCOUNT demo:types:hll:uv:2026-10-28             # → 5，内存约 12KB

适合看板级 UV；需要精确账单、风控名单时不要用。多个 HLL 可以用 PFMERGE 合并。

Geo：把经纬度塞进 ZSet

Geo 没有独立的数据结构：它把经纬度编码成 geohash 存进 ZSet 的 score， 所以 ZREM 之类的命令也能用。查询时按半径过滤并带出距离。

Redis 命令
# 写入店铺坐标（经度、纬度、名称）
GEOADD demo:types:geo:shops 116.404 39.915 天安门 116.417 39.909 王府井 ...

# 以天安门为圆心找 3km 内的店，同时带出距离和坐标
GEOSEARCH demo:types:geo:shops FROMLONLAT 116.404 39.915 BYRADIUS 3 km WITHDIST WITHCOORD
# → 天安门 0km、王府井 1.29km、前门 1.42km；上海外滩超出半径被排除

# 两点直线距离，单位 km
GEODIST demo:types:geo:shops 天安门 王府井 km   # → 1.2942
demo-redis/.../types/DataTypeService.java
// fromCoordinate 是圆心，Distance(3, KILOMETERS) 是半径
GeoResults<GeoLocation<String>> results = redis.opsForGeo().search(key,
        GeoReference.fromCoordinate(new Point(116.404, 39.915)),
        new Distance(3, Metrics.KILOMETERS),
        // 不显式 include，getPoint()/getDistance() 会拿到 null
        RedisGeoCommands.GeoSearchCommandArgs.newGeoSearchArgs()
                .includeCoordinates().includeDistance());

精度受 geohash 位数限制，城市级「附近」足够；高精度轨迹、路径规划不要用它。

Stream：Redis 版消息队列

Stream 是唯一自带「消费进度」的类型：消息追加写、消费者组分配、 消费后进入 pending，XACK 才算确认。消费失败的消息留在 pending， 可以用 XPENDING / XCLAIM 重投。

Redis 命令
# 追加两条消息，* 表示由 Redis 生成消息 ID（时间戳-序号）
XADD demo:types:stream:orders * orderId ORD-1001 status CREATED
XADD demo:types:stream:orders * orderId ORD-1002 status PAID

# 按 ID 范围读全部消息
XRANGE demo:types:stream:orders - +

# 创建消费者组，0 表示从第一条开始消费
XGROUP CREATE demo:types:stream:orders order-group 0

# 投递给 consumer-1：消息进入 pending，但还没确认
XREADGROUP GROUP order-group consumer-1 STREAMS demo:types:stream:orders >

# XACK 之后才从 pending 移除；不 ACK 就一直留在 pending 里
XACK demo:types:stream:orders order-group 1793188192568-0
✓

什么时候用 Stream，什么时候用 MQ Stream 轻量、无需额外组件，适合中小规模事件流或本地可靠队列； 跨团队、大吞吐、需要死信/延迟/事务消息时，还是 RabbitMQ / RocketMQ 更合适 （见 消息中间件实战）。

03限流：六种算法，回答同一个问题

限流器只做两件事：这次请求放不放？如果拒绝，客户端等多久再来？ 不同算法的差别，全在「怎么记住过去这段时间的请求」。

先把窗口想成一个滑动的时间框：任何时刻往前看 N 秒，框里的请求数不能超过 limit。 固定窗口把它切成一个个格子，滑动日志把每次请求都记下来，双窗口只记两个计数， 分桶记 N 个小格子，令牌桶/漏桶则换成「按速率补充/漏出」的模型。

固定窗口：最简单，也最容易在边界翻倍

把时间轴按窗口长度切开，每个窗口一个计数器。窗口编号用 floor(now / windowMs) 计算，计数存进 Hash 的对应字段。 实现简单、内存固定，但窗口边界会漏过接近两倍的流量。

demo-redis/.../support/LuaScripts.java · FIXED_WINDOW
-- ARGV: 1=当前毫秒时间戳 2=窗口长度 3=上限
local now = tonumber(ARGV[1])
local windowMs = tonumber(ARGV[2])
local limit = tonumber(ARGV[3])

-- 窗口编号对齐时间轴：同一窗口的请求都落在同一个 Hash 字段
local windowIndex = math.floor(now / windowMs)
-- 读出当前窗口已放行的数量，没有则当 0
local current = tonumber(redis.call('HGET', KEYS[1], tostring(windowIndex)) or '0')
if current >= limit then
    -- 拒绝：返回「允许|剩余|重试毫秒」，重试 = 距离本窗口结束的时间
    return '0|0|' .. (windowMs - (now % windowMs))
end

-- 放行：先自增，再清掉两个窗口之前的旧字段，最后给整个 Hash 续 TTL
current = redis.call('HINCRBY', KEYS[1], tostring(windowIndex), 1)
redis.call('HDEL', KEYS[1], tostring(windowIndex - 2))
redis.call('PEXPIRE', KEYS[1], windowMs * 2)
-- 剩余名额 = 上限 - 已放行数
return '1|' .. (limit - current) .. '|0'

这里用「窗口编号对齐时间轴」而不是「第一次请求开始计时」， 这样边界实验才能稳定复现。最后的 PEXPIRE 保证旧窗口字段会被清理。

滑动日志：每次请求都记一笔，最精确

ZSet 的 score 存请求时间戳，每次先删掉窗口外的记录，再数窗口内有多少条。 精确，但请求量大时 ZSet 会很长，清理和内存都是成本。

demo-redis/.../support/LuaScripts.java · SLIDING_WINDOW_LOG
-- 先删掉滑出窗口的记录（score 存的是请求时间戳，单位 ms）
redis.call('ZREMRANGEBYSCORE', KEYS[1], 0, now - windowMs)
-- 剩下的条数就是窗口内的请求数
local count = redis.call('ZCARD', KEYS[1])
if count >= limit then
    -- 最早那条记录滑出窗口还需要多久 = 它的 score + 窗口长度 - 现在
    local oldest = redis.call('ZRANGE', KEYS[1], 0, 0, 'WITHSCORES')
    local retry = 0
    if oldest[2] then
        retry = tonumber(oldest[2]) + windowMs - now
    end
    if retry < 0 then retry = 0 end
    return '0|0|' .. retry
end
-- 放行：本次请求也记一条，score 用当前时间；TTL 多留 1s 兜底
redis.call('ZADD', KEYS[1], now, member)
redis.call('PEXPIRE', KEYS[1], windowMs + 1000)
-- 减 1 是因为刚把自己加进 ZSet
return '1|' .. (limit - count - 1) .. '|0'

返回的 retry 是「最早那条记录滑出窗口」还需要多久，比直接让客户端等一个完整窗口更友好。

双窗口计数：内存固定，近似平滑

只存当前窗口和上一窗口的计数，用当前时间在窗口里的进度做加权： 上一窗计数 × 剩余比例 + 当前窗计数。 比固定窗口平滑得多，代价是临界值附近只是估算。

demo-redis/.../support/LuaScripts.java · SLIDING_WINDOW_COUNTER
-- 前置：脚本开头已从 Hash 读出上一窗口 previous 和当前窗口 current
-- elapsed = 当前窗口已经过去的比例（0 ~ 1）
local elapsed = (now % windowMs) / windowMs
-- 上一窗口按剩余比例衰减，再加上当前窗口的计数，得到近似滑动值
local estimated = previous * (1 - elapsed) + current
if estimated + 1 > limit then
    -- 拒绝：剩余额度向下取整；重试时间 = 等到下一个窗口
    local retry = windowMs - (now % windowMs)
    if retry < 1 then retry = 1 end
    return '0|' .. math.floor(limit - estimated) .. '|' .. retry
end
-- 放行：当前窗口计数 +1，TTL 覆盖两个窗口
redis.call('HINCRBY', KEYS[1], tostring(currentWindow), 1)
redis.call('PEXPIRE', KEYS[1], windowMs * 2)

Redis 官方常用的近似算法。它的「剩余额度」可能是小数被向下取整， 所以更适合做保护阈值，而不是精确配额。

滑动分桶：精度和内存之间的旋钮

把一个窗口切成 N 个桶（本实现 N=10），每次累加最近 N 个桶的计数。 桶越多越接近滑动日志，桶越少越省内存。拒绝时从最旧的桶开始累加， 找到「腾出一个名额」的时间点作为重试等待。

demo-redis/.../support/LuaScripts.java · SLIDING_WINDOW_BUCKET
-- 每个桶的时长 = 窗口 / 桶数（本实现桶数 10）
local bucketMs = math.floor(windowMs / buckets)
-- 当前桶编号，桶编号同样对齐时间轴
local current = math.floor(now / bucketMs)
-- 累加最近 buckets 个桶：等价于「过去一个窗口」的请求数
local sum = 0
for i = 0, buckets - 1 do
    local value = redis.call('HGET', KEYS[1], tostring(current - i))
    if value then sum = sum + tonumber(value) end
end
if sum >= limit then
    -- 需要腾出的名额数
    local overflow = sum - limit + 1
    local freed = 0
    local retry = bucketMs
    -- 从最旧的桶开始累计，凑够 overflow 时的桶边界就是重试时间
    for i = buckets - 1, 0, -1 do
        local index = current - i
        local value = tonumber(redis.call('HGET', KEYS[1], tostring(index)) or '0')
        freed = freed + value
        if freed >= overflow then
            retry = (index + 1) * bucketMs - now
            break
        end
    end
    if retry < 1 then retry = 1 end
    return '0|0|' .. retry
end
-- 放行：只在当前桶 +1
redis.call('HINCRBY', KEYS[1], tostring(current), 1)
!

重试时间不能拍脑袋 最初版本直接用「最旧桶的过期时间」当 retry，但最旧桶可能根本没有请求， 结果返回 0ms，测试直接抓到。正确做法是累计到「足够腾出一个名额」的那个桶。

令牌桶：允许突发，按速率补充

桶里最多放 capacity 个令牌，按 capacity / window 的速率持续补充。 请求来了先拿一个令牌，拿不到就拒绝。它允许短时突发（桶里攒着令牌）， 但长期平均速率被限制住。

demo-redis/.../support/LuaScripts.java · TOKEN_BUCKET
-- 距上次请求过去了多少秒（时钟回拨时按 0 处理）
local elapsed = math.max(0, now - ts) / 1000
-- 按补充速率加令牌，但不超过桶容量：这就是「允许突发」的来源
tokens = math.min(capacity, tokens + elapsed * refillPerSec)
if tokens >= 1 then
    -- 够一个令牌就放行，并扣掉
    tokens = tokens - 1
    allowed = 1
else
    -- 不够：算出还差多少毫秒才能攒够 1 个令牌
    retry = math.ceil((1 - tokens) / refillPerSec * 1000)
end
-- 无论放行与否，都回写令牌余额和时间戳
redis.call('HSET', KEYS[1], 'tokens', tostring(tokens), 'ts', tostring(now))

令牌桶关心「能不能马上处理」，适合保护下游 API；它不保证请求之间的间隔均匀。

漏桶：请求先入桶，再匀速漏出

漏桶把请求当成水：桶有容量，底部按固定速率漏水。桶满就拒绝。 它保证输出速率恒定，适合削峰、保护慢速下游；代价是不允许突发。

demo-redis/.../support/LuaScripts.java · LEAKY_BUCKET
-- 距上次请求过去多少秒，期间桶里的水按漏出速率减少
local elapsed = math.max(0, now - ts) / 1000
level = math.max(0, level - elapsed * leakPerSec)
if level + 1 <= capacity then
    -- 还有空间：请求入桶，level +1
    level = level + 1
    allowed = 1
else
    -- 桶满：算出要等多久才能腾出 1 个单位
    retry = math.ceil((level + 1 - capacity) / leakPerSec * 1000)
end
-- 回写当前水位和时间戳
redis.call('HSET', KEYS[1], 'level', tostring(level), 'ts', tostring(now))

04分布式锁：从 SETNX 到看门狗

锁要同时满足三件事：互斥（同一时刻只有一个持有者）、 不会死锁（持有者崩溃后能自动释放）、 不会误删（A 不能释放 B 的锁）。缺一个，线上就会出事故。

先看一个错误实现

最直觉的写法是两步：SETNX lock 1 占位，成功后再 EXPIRE lock 30。 问题在于这两步不是原子的：如果进程在两者之间崩溃，锁就永远没有过期时间。

错误：两条命令

  • SETNX 成功
  • 进程崩溃 → 没执行 EXPIRE
  • 锁永不过期，所有实例永久阻塞

正确：一条命令

  • SET key holder NX PX 30000
  • 占位和过期时间一次完成
  • Spring Data：setIfAbsent(key, holder, Duration)

第二件事是「只删自己的锁」。如果直接 DEL，会出现这样的时间线： A 的业务超时、锁自动过期、B 拿到锁，然后 A 执行完把 B 的锁删了。 正确做法是把持有者标识写进 value，用 Lua 比较后再删。

demo-redis/.../lock/SimpleRedisLock.java
public boolean tryLock(String key, String holder, long ttlMillis) {
    // SET key holder NX PX ttl：占位和过期时间一条命令完成
    return Boolean.TRUE.equals(redis.opsForValue()
            .setIfAbsent(key, holder, Duration.ofMillis(ttlMillis)));
}

/** 只有仍是自己持有时才删除，避免误删别人的锁。 */
public boolean unlock(String key, String holder) {
    // GET 比较 + DEL 必须在同一段 Lua 里原子完成
    Long result = redis.execute(releaseScript, List.of(key), holder);
    return result != null && result == 1L;
}
demo-redis/.../support/LuaScripts.java · LOCK_RELEASE
-- value 不等于自己的 holder，说明锁已过期并被别人拿走，直接返回 0

    -- 只有确认是自己的锁才删，返回 1 表示释放成功
    return redis.call('DEL', KEYS[1])
end
return 0

锁的过期时间，到底设多长？

设短了，业务没跑完锁就过期，互斥失效；设长了，进程崩溃后别人要等很久。 这个矛盾没有静态答案，于是有了看门狗： 业务还在跑，就定期把锁的过期时间续回去；业务结束或进程崩溃，续期停止，锁自然过期。

手写看门狗

本仓库的 SimpleLockService 用一个定时任务模拟：每 ttl/3 调一次 LOCK_RENEW，Lua 先比较 holder，再 PEXPIRE。 实验参数 ttl=1500ms、hold=4000ms：

demo-redis/.../lock/SimpleLockService.java
// 续期间隔 = TTL / 3，留两次重试余量；下限 100ms 防止空转
long interval = Math.max(ttlMillis / 3, 100);
scheduler.scheduleAtFixedRate(() -> {
    // 业务已结束就不再续期，让锁自然过期
    if (!aHolding.get()) {
        return;
    }
    // LOCK_RENEW 内部先比较 holder 再 PEXPIRE，不会续别人的锁
    boolean ok = lock.renew(key, holderA, ttlMillis);
    if (ok) {
        renewed.set(true);
        events.add(new Event(elapsed(start), "A", "watchdog renew", true,
                "每 " + interval + "ms 续期到 " + ttlMillis + "ms"));
    }
}, interval, interval, TimeUnit.MILLISECONDS);

并发计数：锁到底防住了什么

这段代码模拟「读 → 处理 1ms → 写回」。20 个线程各 50 次，期望 1000：

demo-redis/.../lock/RedissonLockService.java
if (locked) {
    // 读改写整段在锁内，其他线程无法插入
    lock.lock();
}
try {
    int current = value[0];
    sleep(1);                      // 放大「读」和「写」之间的窗口
    value[0] = current + 1;
} finally {
    // 只释放自己持有的锁
    if (locked && lock.isHeldByCurrentThread()) {
        lock.unlock();
    }
}

加锁后慢了一个数量级，因为每次 +1 都要两次 Redis 往返（加锁、解锁）。 这也是为什么锁的粒度要小、临界区要短：能不用锁就不用，必须用就别把慢操作放进去。

!

单 Redis 锁的边界 主从异步复制时，主节点刚返回加锁成功就宕机，从节点可能还没收到这把锁，新主上别人能再次加锁。 对一致性要求极高的场景，需要 RedLock（仍有争议）或带 fencing token 的方案： 每次加锁拿到递增编号，下游只接受更大的编号，从而丢弃过期持有者的写入。

05缓存一致性：延迟双删到底删什么

缓存旁路（Cache Aside）只有两条规则：读的时候先查缓存、未命中回源并回填； 写的时候先改数据库、再删缓存。真正难的是删除和回填撞在一起的那几百毫秒。

把缓存想成贴在数据库旁边的一张便签。写操作把便签撕掉，下一次读会重新抄一张。 问题出在「读线程已经读到了旧值、还没抄完」的时候：写线程撕掉便签、更新数据库， 读线程随后把刚读到的旧值抄了上去。这张旧便签会一直留到 TTL 过期。

为什么是删除，而不是更新缓存

更新缓存

  • 两个写请求并发，后到的可能先算完，缓存留下旧值
  • 缓存值可能需要复杂计算，每次都算很浪费
  • 缓存里可能存的是聚合结果，更新逻辑难写

删除缓存

  • 下一次读自然回源，拿到数据库当前值
  • 逻辑简单，失败重试也容易
  • 代价是短时间多一次回源

竞态时间线

本仓库的 POST /api/redis/cache/race?id=99 用两个线程把这条时间线固定下来： 读线程先查库拿快照，再 sleep(500)；写线程在 100ms 后更新 DB、删缓存、 登记延迟删除；读线程醒来把旧快照回填；延迟队列到点执行第二次删除。

延迟队列：ZSet 的 score 就是闹钟

ZADD queue <dueAt> cacheKey 把任务按到期时间排好。 后台线程每 200ms 取 score <= now 的任务，先 ZREM 再删除缓存。 先移除再执行，保证多个实例同时轮询时只有一个能领到任务。

demo-redis/.../cache/DelayTaskQueue.java
public long schedule(String cacheKey, long delayMillis) {
    // score = 到期时间戳，ZSet 自动按到期先后排序
    long dueAt = System.currentTimeMillis() + delayMillis;
    redis.opsForZSet().add(QUEUE_KEY, cacheKey, dueAt);
    return dueAt;
}

@Scheduled(fixedDelay = 200, initialDelay = 200)
public void poll() {
    long now = System.currentTimeMillis();
    // 每轮最多领 20 个已到期任务，避免一次拉太多
    Set<String> due = redis.opsForZSet().rangeByScore(QUEUE_KEY, 0, now, 0, 20);
    for (String cacheKey : due) {
        // 先 ZREM 抢任务：多实例同时轮询时，只有一个能删成功
        Long removed = redis.opsForZSet().remove(QUEUE_KEY, cacheKey);
        if (removed != null && removed > 0) {
            redis.delete(cacheKey);
        }
    }
}

延迟双删的边界

  • 不是强一致：延迟窗口内仍可能读到旧值，只是把窗口从「TTL」缩短到「延迟时间」。
  • 延迟时间靠猜：要大于「读线程回源 + 回填」的最长耗时；太长会让脏值活得更久，太短挡不住。
  • 删除可能失败：网络抖动、Redis 不可用都会让第二次删除落空，需要重试或补偿。
  • 主从延迟：写完主库立刻删缓存，读请求可能从从库读到旧值再回填。延迟双删也挡不住这种情况。

对一致性要求更高时，常见方案是「订阅 binlog（Canal 等）异步删缓存」或「缓存版本号 + 短 TTL」； 延迟双删是成本低、易落地的折中，不是银弹。
