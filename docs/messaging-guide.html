01心智模型：先想清楚消息怎么走

两个中间件最容易被混淆的地方，是把「交换机」「队列」「Topic」「分区」当成同一层概念。 先把每个名词对应的职责分开，后面所有问题都会变得直观。

RabbitMQ：交换机决定去向，队列负责存储

可以把 RabbitMQ 想成一个快递分拣中心：生产者把包裹交给 Exchange（分拣中心）， 分拣中心根据 Binding（路由规则） 把包裹放进不同的 Queue（快递柜）， 消费者从快递柜取件。Exchange 本身不存消息，消息真正待的地方是队列。

  • Exchange 类型决定匹配方式：fanout 全部投递、direct 精确匹配 routing key、topic 通配符匹配。
  • 默认交换机 "" 是一个特殊的 direct exchange，routing key 直接写队列名，Demo 里大量使用。
  • 一条消息可以被复制到多个队列（fanout / topic 多绑定），每个队列各存一份。
  • 同一个队列挂多个消费者就是 competing consumers：消息被轮流取走，不保证谁先处理完。

RocketMQ：队列决定顺序，位点决定进度

RocketMQ 更像一条有多条车道的高速公路：Topic 是这条路的名字， MessageQueue 是具体车道，消息按队列追加写进 Broker 的 CommitLog。 消费者组记录自己每条车道走到哪里（offset），消费后消息不会立刻删除， 只是位点前移，所以可以重置位点重放。

  • NameServer 无状态、彼此不通信，Producer / Consumer 从它那里拿 Topic 路由并缓存。
  • Broker 把消息顺序追加到 CommitLog；Topic 只是逻辑视图，消息按队列分片存储。
  • PushConsumer 本质是拉取：客户端长轮询拉消息，再交给监听器，所以积压时位点会停住。
  • 消费不删除消息，位点前移即可；保留期内可以重置 offset 重放，这是和 RabbitMQ 最大的差异之一。

角色关系：一个队列能挂几个消费者？

很多困惑不是 API 不会用，而是没把角色之间的数量关系想清楚：谁和谁是一对多、 一条消息会被复制几份、消费者加到什么时候就不再加了。先把关系画出来，扩容和顺序才有判断依据。

RabbitMQ：生产者只认交换机，消费者只认队列

关系基数含义与边界
Producer → Exchange N : N 生产者只声明「发到哪个 exchange + routing key」，不需要知道队列存在。一个生产者可以发多个 exchange，多个生产者也可以发同一个。
Exchange → Queue M : N（靠 binding） 一个 exchange 可以绑多个队列，一个队列也能被多个 exchange 绑定。一条消息匹配到几个队列就复制几份，每个队列各一份。
Broker ↔ Exchange / Queue 1 : N Exchange 和 Queue 都声明在 Broker 上，按 vhost 隔离；连接和信道只是客户端到 Broker 的传输通道，不改变路由关系。
Queue → Consumer 1 : N（竞争） 同一个队列可以挂任意多个消费者，消息轮流投给其中一个，一条消息只被一个消费者处理。消费者可以在同一个进程，也可以是多个应用实例。
Queue → Consumer 1 : 0 没有消费者时消息留在队列里，表现为积压；这也是「先生产、后消费」能工作的原因。
Consumer → Queue 1 : N 一个监听容器可以同时监听多个队列（如 @RabbitListener(queues = {a, b})），但每条消息仍然只属于一个队列，不会跨队列重复。
Consumer ↔ Consumer 无组概念 RabbitMQ 没有 ConsumerGroup：挂在同一个队列上的所有消费者天然竞争；不同队列之间互不影响，各消费各的。

本仓库里可以直接对照：WorkConsumer 用 concurrency = "2" 在一个应用内开两个消费者抢 demo.work.queue，UnorderedConsumer 开到 4；而 OrderedConsumer 固定为 1， 因为同一队列一旦有多个消费者，处理顺序就不再可控。

RocketMQ：消费者组是分配单位，队列是并行单位

关系基数含义与边界
ProducerGroup → Topic N : N 生产者组只是发送方身份，用于事务消息回查和运维标识，不参与负载均衡；一个组可以发多个 Topic。
Topic → MessageQueue 1 : N Demo 自动创建的 Topic 默认 4 个队列，创建后队列数固定。队列既是并行单位，也是顺序单位，还是扩容的上限。
Broker ↔ Topic M : N 一个 Broker 承载多个 Topic，一个 Topic 的队列可以分散在多个 Broker 上；NameServer 与 Broker 同样是多对多注册关系。
Producer / Consumer ↔ Broker N : N 消息不经过 NameServer：客户端先从 NameServer 拿路由，再直接和 Broker 收发；NameServer 只负责注册与发现。
Topic ↔ ConsumerGroup M : N 一个组可以订阅多个 Topic（组内实例的订阅关系应保持一致）；一个 Topic 也可以被多个组各自消费，互不影响。
ConsumerGroup → 实例 1 : N 集群消费下组内实例分摊队列：同一队列同一时刻只属于一个实例。实例数超过队列数时，多出的实例分不到队列，只能空转。
MessageQueue → 消费线程 同一时刻 1 个（顺序） 顺序消费会给队列加锁，同一队列在同一时刻只由一个线程处理；并发消费下同一队列可被多线程处理，但顺序不再保证。
ConsumerGroup ↔ Offset 每组每队列 1 个 位点记在「组 + 队列」上，不记在实例上；实例上下线、队列重新分配后，消费进度仍然连续。
广播模式 1 : N（每实例全量） BROADCASTING 下每个实例都消费全部队列，同一条消息在每个实例各处理一次，不能用来分摊压力。
!

同名就是同一个，不是「各消费一份」 RabbitMQ 里两个服务监听同名队列，它们会互相抢消息；RocketMQ 里两个服务用同一个 consumerGroup 订阅同一 Topic，也会被当成同一组的实例来分摊队列。 想让每个服务都拿到全量，RabbitMQ 要用不同队列绑定同一个 exchange， RocketMQ 要么用不同消费者组，要么显式使用广播模式。

同一个问题RabbitMQRocketMQ
一条消息会被几个消费者处理？ 同一队列内 1 个；若消息被路由到多个队列，则每个队列的副本各由 1 个消费者处理 集群消费：组内 1 个实例；广播消费：每个实例各处理 1 次
加消费者能一直提升并行度吗？ 能加，理论上不设上限；但受 prefetch、数据库和下游能力限制，且同队列不再保证顺序 不能超过队列数；多出的实例分不到队列，只会空转
消费者之间怎么分工？ 同一队列竞争抢消息，Broker 轮流投递（prefetch 影响是否均匀） 组内按队列分配，队列内部再按消费线程并发；顺序消费时串行
消费进度记在哪？ 没有显式位点，以未 ACK 消息和队列状态体现 每个「消费者组 + 队列」一个 offset，实例重分配后接着消费
消费者全部下线会怎样？ 消息留在队列里积压，重新上线后继续消费 位点停住，消息留在 CommitLog，实例恢复后从 offset 继续
i

记住两个上限 RabbitMQ 的并行度看消费者数量 × prefetch，可以超过队列数； RocketMQ 的并行度看队列数 × 消费线程，消费者实例再多也超不过队列数。 需要顺序时，两边都要把并行度收回到 1：RabbitMQ 单队列单消费者，RocketMQ 单队列顺序消费。

✓

记住一句话就够了 RabbitMQ 的核心问题是「这条消息该去哪个队列」，RocketMQ 的核心问题是 「这条消息属于哪个队列、这个队列消费到哪了」。后面五个可靠性问题，都是从这两句话延伸出来的。

02RabbitMQ 深入：把「可靠」拆成三段

RabbitMQ 的可靠性不是一个开关，而是三段时间：发布时 Broker 有没有收下、路由时有没有落到队列、 消费时业务有没有处理完。三段分别对应 Confirm、Return、ACK，任何一段缺失都只能算「可能送达」。

死信队列：处理不了的消息去哪

死信队列（DLX / DLQ）不是独立功能，而是普通队列的一组参数：当消息被拒绝且不重入队、 TTL 过期、或队列满时，Broker 把它转发到指定的 exchange。Demo 的主队列同时配置了 x-dead-letter-exchange、x-dead-letter-routing-key 和 3 秒 TTL。

消费语义：ACK 不是「收到」，是「处理完」

  • Spring AMQP 默认 AUTO：监听方法正常返回后由容器 ACK；抛异常则 nack。
  • nack 默认重新入队（defaultRequeueRejected=true），处理逻辑一直失败就会无限重投。 对不可恢复的错误，用 AmqpRejectAndDontRequeueException 或 default-requeue-rejected: false 切断循环，再交给 DLQ。
  • prefetch 控制一个消费者最多预取多少条未 ACK 消息。预取越大吞吐越高，但单实例囤积越多、故障重投越多，优先级效果也越差。
  • 幂等不能省：ACK 丢失、消费者崩溃、网络抖动都会导致重投，Broker 只保证 at-least-once。
✓

RabbitMQ 侧的小结 路由靠 Exchange + Binding；发布可靠靠 Confirm + Return；消费可靠靠手动 ACK + 幂等； 失败兜底靠 DLQ。四件事各管一段，不能互相替代。

03RocketMQ 深入：队列、位点与事务

RocketMQ 把「顺序」和「回溯」做进了存储模型：消息按队列追加写，消费只移动位点。 理解这一点，顺序消息、积压、持久化、重放这些行为就都能推导出来。

整体架构：四个角色，一条 CommitLog

  • NameServer：路由注册中心，无状态、节点之间不通信。Producer 发送前拉取 Topic 路由并缓存，Broker 定时上报心跳。
  • Broker：存储与投递。消息顺序写 CommitLog，再异步构建 ConsumeQueue 索引；Topic 的队列数决定消费并行度。
  • Consumer Group：同一组内分摊队列（CLUSTERING）；不同组之间互不影响，各自消费全量。
  • offset：每个队列的消费进度。暂停、重启、扩容都围绕位点变化；重置位点就能重放历史消息。
i

自动创建 Topic 的队列数 本 Demo 没有预建 Topic，第一条消息发送时自动创建，默认 4 个队列。 这意味着顺序消费最多有 4 个并行度，积压时加机器也无法超过队列数。 生产通常预建 Topic，并按吞吐规划队列数。

4.1 幂等：重复投递一定会发生

先接受一个事实：端到端的 exactly-once 很难靠中间件单独保证。 生产者超时重发、Broker 重投、消费者 ACK 丢失、实例重启、RocketMQ rebalance， 任何一个环节都可能让同一条业务消息被处理两次。工程上的标准答案是 at-least-once 投递 + 消费端幂等。

错误做法

  • 用 Broker 生成的 messageId 去重：生产者重发会生成新 ID，跨系统也不通用。
  • 先查「处理过没有」，再写业务：并发下两个线程同时查到「没处理」，各写一次。
  • 先执行业务、后登记去重：登记前崩溃，重投时又执行一遍。
  • 登记后业务失败却不撤销：消息被永久当成重复，业务再也没机会重试。

正确做法

  • 消息体里带稳定的业务唯一键（订单号、事件 ID），重投保持不变。
  • 用原子操作抢占：内存 compute、Redis SET NX EX、数据库唯一索引。
  • 先抢占、再处理，成功后保留记录；失败则删除记录并抛出异常，让重投能重新处理。
  • 去重记录设置 TTL，覆盖最大重试窗口；生产环境多实例共享存储。
demo-rabbitmq/.../support/InMemoryIdempotentStore.java（RocketMQ 模块同名实现）
public boolean tryAcquire(String scene, String messageId) {
    String key = scene + ":" + messageId;
    long now = System.currentTimeMillis();
    boolean[] first = {false};
    // compute 对同一个 key 是原子的：并发拿到同一条消息时只有一个线程能看到 null
    expireAtByKey.compute(key, (ignored, expireAt) -> {
        if (expireAt == null || expireAt <= now) {
            first[0] = true;
            return now + TTL_MILLIS;
        }
        return expireAt;
    });
    cleanupIfNeeded(now);
    return first[0];
}

public void release(String scene, String messageId) {
    // 业务失败时撤销登记，让重投有机会重新处理
    expireAtByKey.remove(scene + ":" + messageId);
}

4.2 顺序：生产、存储、消费，一环都不能乱

「消息乱序」通常不是 Broker 的默认行为，而是三个环节里有一个没约束住： 生产端并发发送、消息被分散到多个队列、 消费端多线程处理。要让顺序成立，必须三件事同时成立。

错误做法

  • 同一个队列挂多个消费者，却期望消息按序处理（competing consumers 必然打乱）。
  • 生产端循环 convertAndSend，以为「代码里是顺序的」就等于「入队是顺序的」。
  • 消费失败就吞掉异常继续处理下一条，失败消息被跳过，后续状态直接错乱。
  • RocketMQ 用普通发送 + 默认并发消费，却期望同一订单严格有序。

正确做法

  • 按业务 key 分区：同一订单 / 用户固定进同一个队列，队列内只用一个消费者。
  • RabbitMQ 开启 confirm 时，把整批发送放进 rabbitTemplate.invoke，绑定同一个 channel。
  • RocketMQ 用 syncSendOrderly + ConsumeMode.ORDERLY。
  • 失败不要跳过：重试、阻塞当前分区，超过次数再转 DLQ 并告警。
!

RabbitMQ 最容易踩的坑：confirm 让发布顺序失效 开启 publisher confirm 后，一个 channel 在确认返回前不会归还连接池。 循环里的 convertAndSend 可能落到多个 channel 上，而 Broker 只保证同一个 channel 内的发布顺序。 实测只把消费者改成 concurrency = 1 时，日志仍会出现 step-4 / 5 / 6 交错。 发送端必须用 invoke 把整批消息钉在同一个 channel 上，并等待确认。

4.3 积压：先量深度，再谈扩容

积压是「生产速率 > 消费速率」的结果，可能是一次性峰值，也可能是消费者变慢、下游故障、 毒消息卡住队列。处理积压的第一步不是加机器，而是确认堆积量、增速和消费速率。

错误做法

  • 只看应用日志，不看队列深度和消费位点。
  • RocketMQ 队列只有 4 个，却指望加 10 个实例提升并行度（消费者数超过队列数没有意义）。
  • prefetch 调得很大，单实例囤一堆消息；实例一挂，全部重投，雪崩。
  • 毒消息无限重试，把整个队列堵死。
  • 为了削峰把消息无限堆在应用内存里，进程一重启全丢。

正确做法

  • RabbitMQ 看 Ready / Unacked；RocketMQ 看 Dashboard 的 Diff（最大位点 - 消费位点）。
  • 先确认是「消费慢」还是「生产突增」，再决定扩容、限流还是降级。
  • 扩容前确认下游容量；数据库往往先成为瓶颈。
  • 配置重试上限 + DLQ，毒消息及时隔离并告警。
  • 用暂停 / 恢复演练验证消费能力和恢复时间。

4.4 持久化：别把「写进内存」当成「不会丢」

持久化要回答两个问题：Broker 重启后消息还在吗？机器断电后消息还在吗？ 两个中间件的默认值和保证强度不同，但共同点是：持久化只保证「不丢」，不保证「只消费一次」。

错误做法

  • 队列 durable，但消息设成 NON_PERSISTENT，以为队列持久化就万事大吉。
  • 生产者 fire-and-forget，不看 confirm，Broker 拒绝或路由失败都不知道。
  • 消费者开启自动 ACK，消息一到就确认，处理到一半崩溃就彻底丢了。
  • 本地验证用 docker compose down，容器和数据卷一起删掉，误判成「持久化失效」。
  • 单 Broker 无副本，却把它当成金融级可靠存储。

正确做法

  • RabbitMQ 三个条件同时满足：durable queue + persistent message + durable exchange。
  • 生产端开启 confirm，失败可重发；必要时开启 mandatory + return。
  • 消费端处理成功后再 ACK；失败重试，最终进 DLQ。
  • RocketMQ 用 syncSend，强可靠场景开同步刷盘 + 副本。
  • 生产环境挂持久化卷、做备份、监控磁盘和副本状态。

4.5 优先级：先处理谁，以及它的边界

优先级不是「可靠」问题，而是资源有限时的调度策略。它只在消息排队时起作用， 不能抢占已经在处理的消息，也不能替代容量规划。两个中间件的实现路径完全不同： RabbitMQ 有原生优先级队列，RocketMQ 没有消息级优先级，只能靠 Topic / 队列隔离。

错误做法

  • 消费者一直空闲，发消息时设优先级，期望「高优先级先处理」——消息一到就被取走了，没有排队可比较。
  • 在消费端根据消息头排序，但消息已经被多线程同时取走，顺序无法改变。
  • RocketMQ 在消息属性里塞 priority，以为 Broker 会排序（Broker 只按 FIFO）。
  • 设 100 个优先级，或把核心链路和大流量低优先级混在一个队列。
  • 认为「高优先级」可以无限插队，不考虑低优先级被饿死。

正确做法

  • RabbitMQ 声明 x-max-priority，在消息属性里设置优先级；用暂停 / 恢复制造排队再观察。
  • 优先级敏感时把 prefetch 调小，避免一次预取太多低优先级消息。
  • RocketMQ 按优先级拆 Topic + 独立消费者组，做资源隔离；低优先级可单独暂停、限流、扩容。
  • 核心链路用独立队列 / 独立消费者，而不是只靠优先级数值。
  • 为低优先级设计老化或保底配额，避免长期饥饿。

放大看：优先级队列内部是多个 FIFO 子队列

x-max-priority = 10 并不是让一条队列按优先级全局排序，而是让 Broker 在内部维护 0～10 共 11 条子队列。入队时按消息的 priority 放进对应子队列； 出队时从最高的非空子队列开始取，某一档空了才轮到下一档。每个子队列内部仍然是 FIFO。

05选型与生产清单

选型不是「谁更先进」，而是「哪组约束更重要」。先列出必须满足的约束，再看哪个中间件的默认能力更接近， 最后用工程手段补齐差距。

一个务实的判断顺序 先看投递语义和顺序要求，再看吞吐与堆积规模， 然后看路由灵活性和运维成本。不要因为「RocketMQ 吞吐高」就把一个只需要 路由分发的内部系统迁过去，也不要因为「RabbitMQ 简单」就让它承担海量事件流。

上线前检查清单

  • 业务唯一 ID：每条消息都有稳定的业务键，消费端有原子去重（Redis / DB 唯一索引）。
  • 发送可靠：RabbitMQ 开 confirm；RocketMQ 用 syncSend 或带回调的 async；失败有重试和补偿。
  • 本地事务一致性：要么用 RocketMQ 事务消息，要么用 Outbox / 本地消息表，不能「先写库再随手发」。
  • 消费重试上限：配置最大重试次数，超过后进入 DLQ，并有告警和人工处理入口。
  • ACK 时机：业务处理成功后再 ACK / 提交位点，不要自动 ACK。
  • 持久化与副本：RabbitMQ durable + persistent + 持久化卷；RocketMQ CommitLog + 副本 + 刷盘策略。
  • 顺序 key 设计：key 稳定、分布均匀；评估热点和扩容重新哈希的影响。
  • 积压监控：RabbitMQ 监控 Ready / Unacked；RocketMQ 监控 Diff 和消费 RT；设置阈值告警。
  • 容量与降级：知道单实例消费能力、下游瓶颈和降级开关；积压时有削峰 / 限流方案。
  • 优先级隔离：核心链路独立队列 / Topic / 消费者；不要只靠 priority 数值。
  • 消息契约：字段只增不删、版本兼容、消费端能处理未知字段；大消息走对象存储。
  • 可观测性：日志带 traceId / messageId / 业务键，能从一个订单追到生产和消费两端。
  • 演练：Broker 重启、网络抖动、消费者下线、重复投递、位点重放，至少各做一次。

常见反模式

反模式

  • 把消息中间件当数据库，依赖「消息一定在」做唯一数据源。
  • 消费者里做长事务、同步调用多个下游，吞吐被一个慢服务拖死。
  • 用消息体传巨大文件，Broker 磁盘和网络被打满。
  • 所有业务共用一个 Topic / 队列，出问题互相影响。
  • 重试没有上限，失败消息无限循环。

替代做法

  • 消息只做「事件通知」，权威数据仍在数据库。
  • 消费逻辑短小，重活异步拆给下游或线程池。
  • 大消息存对象存储，消息体只放引用和元数据。
  • 按业务域 / 优先级拆 Topic / 队列 / 消费者组。
  • 重试 → 延迟重试 → DLQ，每层都有指标和告警。
