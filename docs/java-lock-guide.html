02心智模型：锁到底保护什么

先纠正一个最常见的误解：锁不会让代码变快。它把“多个线程可以同时读改写”改成“同一时刻只有一个线程能改”，用并行度换正确性。

i
一句话

锁保护的是共享可变状态，不是某段代码。两个线程锁不同的对象，等于没锁；没有共享状态，就不需要锁。

互斥

同一时刻只有一个线程进入临界区。这是锁最直观的作用，也是本页大部分实验观察的对象。

可见性

synchronized 的 monitorexit 与后续 monitorenter 建立 happens-before；ReentrantLock 的 unlock 与后续 lock 同样保证之前的写入可见。

排队与唤醒

竞争失败的线程进入等待结构，释放时被唤醒。公平性、可中断、超时，都是围绕这个等待结构做文章。

能力synchronizedReentrantLock
可重入是是（AQS state 计数）
公平锁不支持new ReentrantLock(true)
等待可中断否，monitorenter 不响应 interrupt是，lockInterruptibly()
超时获取否是，tryLock(timeout, unit)
条件队列wait/notifyCondition，可多个
等待时的线程状态BLOCKEDWAITING / TIMED_WAITING
释放方式自动退出同步块手动 unlock()，必须放 finally
✓
读快照前先记住这个区别

看到 BLOCKED，说明线程卡在 monitor 入口；看到 WAITING 且栈顶是 Unsafe.park，说明它卡在 AQS 队列。后面两个实验的快照都依赖这个判断。

3.1synchronized：把并发变成串行

一句话：synchronized (monitor) 用对象头里的监视器做互斥，进入时 monitorenter，退出时 monitorexit。

i
类比

一间单人房只有一张门卡。A 刷卡进去后，B 只能站在门口等（BLOCKED）；A 出来交卡，B 才能进。门卡就是 monitor，房间就是临界区。

核心代码

java · SynchronizedLockDemo#run（节选）
Object monitor = new Object();              // 每次请求新建，避免不同请求互相串扰
CountDownLatch startGate = new CountDownLatch(1);
Runnable body = () -> {
    ready.countDown();
    startGate.await();                      // 两个线程都就绪后才一起冲锁
    if (locked) {
        synchronized (monitor) {            // 互斥边界：同一时刻只允许一个线程进入
            enterCritical(...);             // 内部用 AtomicInteger 记录最大并发
        }
    } else {
        enterCritical(...);                 // 反例：没有同步块，两个线程可同时进入
    }
};

四个容易踩的坑

1）锁对象必须是同一个引用；每次 new 一个 Object 去锁，等于没锁。2）sleep() 不释放锁，只有退出同步块才释放。3）锁 this 或 Class 会把无关代码耦合到同一把锁上，优先用私有 final 锁对象。4）等待者处于 TIMED_WAITING 不代表没在等锁，必须看 lockOwner 和栈顶。

3.2ReentrantLock：可重入与 AQS 队列

一句话：ReentrantLock 用 AQS 的 state 记录重入层数，同一线程可以重复 lock()，但 unlock() 次数必须一一抵消。

i
类比

一扇门允许同一个人刷三次卡，但出门也要刷三次；刷多一次会报警（IllegalMonitorStateException），少刷一次门就永远锁着。

核心代码

java · ReentrantLockDemo#run（节选）
lock.lock();                                   // 第 1 层：state 0→1
try {
    lockSteps.add(new LockStep("lock", 1, lock.getHoldCount()));   // 1
    lock.lock();                               // 第 2 层：state 1→2
    lockSteps.add(new LockStep("lock", 2, lock.getHoldCount()));   // 2
    lock.lock();                               // 第 3 层：state 2→3
    lockSteps.add(new LockStep("lock", 3, lock.getHoldCount()));   // 3
    queueReady.await(3, TimeUnit.SECONDS);     // 等 9 个 waiter 全部入队
    Thread.sleep(holdMillis);                  // 持锁一段时间，供队列采样
} finally {
    lock.unlock();                             // 3→2
    lock.unlock();                             // 2→1
    lock.unlock();                             // 1→0，此时才唤醒队首
}

3.3公平锁 vs 非公平锁：谁能在释放瞬间插队

一句话：公平锁在抢锁前先看队列，队列非空就排到队尾；非公平锁跳过检查，直接 CAS 抢，释放者常常能插到最前面。

i
类比

公平锁是取号排队，叫到号才能办；非公平锁是柜台一空出来，谁先挤到窗口谁先办。后者吞吐更高，但等待时间不可预测。

核心代码

java · FairnessDemo#oneRound（节选）
lock.lock();                         // holder 先持有锁
try {
    holderLocked.countDown();
    queueReady.await(3, TimeUnit.SECONDS);   // 等 8 个 waiter 依次入队
    lock.unlock();                   // 释放
    lock.lock();                     // 关键动作：不睡眠，立刻重抢
    acquisitions.add("holder-reacquire");    // 记录 H 的位置
    sleepQuietly(20);
} finally {
    if (lock.isHeldByCurrentThread()) {
        lock.unlock();               // 兜底，避免异常时把锁泄漏给后续轮次
    }
}

公平锁只保证队列中的线程按 FIFO 获得锁，不保证操作系统调度公平，也不保证 tryLock() 公平：tryLock() 不带超时时会直接插队。公平锁还要额外维护队列顺序，吞吐通常低于非公平锁。

3.4等待期中断：monitorenter 与 lockInterruptibly

一句话：synchronized 的等待不可中断，中断只留下标记；lockInterruptibly() 的等待可中断，收到中断立即抛 InterruptedException 并清除标记。

i
类比

synchronized 像排队等电梯，队伍不会因为你接了个电话就让你离开；lockInterruptibly 像排队时允许接电话，接到“立刻回来”的通知就退出队伍。

核心代码

java · InterruptDemo#run（节选）
// synchronized 分支：中断不会取消 monitorenter
synchronized (monitor) {
    victimEntered.set(true);                 // 只有拿到 monitor 才会执行到这里
    timeline.add(new TimelineEvent(..., "entered", "interrupt 未阻止进入"));
}

// ReentrantLock 分支：park 期间响应中断
try {
    lock.lockInterruptibly();                // 等待可被 interrupt 打断
    try {
        victimEntered.set(true);
    } finally {
        lock.unlock();
    }
} catch (InterruptedException e) {
    interruptLatencyMillis.set(...);         // 记录从 interrupt() 到捕获异常的延迟
    exceptionThrown.set(true);
}

3.5死锁：AB-BA 成环、检测与固定顺序修复

一句话：两个线程各持一把锁、又等对方的锁，形成等待环；打破环最直接的办法是让所有线程按同一顺序加锁。

i
类比

两辆车在窄巷相遇：A 车等 B 车倒，B 车等 A 车倒，谁都不动。固定顺序相当于规定“所有车先靠右再前进”，从规则上消除互等。

核心代码

java · DeadlockDemo#crossWorker（节选）
first.lock();                              // 先拿自己那把：T1 拿 A，T2 拿 B
try {
    ownHeld.countDown();
    otherHeld.await(2, TimeUnit.SECONDS);  // 等对方也拿到第一把，确保能成环
    try {
        second.lockInterruptibly();        // 关键：可中断，检测到死锁后才能恢复
        try {
            sleepQuietly(holdMillis);
        } finally {
            second.unlock();
        }
    } catch (InterruptedException e) {
        interrupted.set(true);             // 从等待中醒来，记录并退出
    }
} finally {
    first.unlock();                        // 无论是否死锁，都归还第一把锁
}

4.1租约锁与看门狗：过期接管与到期续期

一句话：租约锁不假设“持有者会永远活着”，而是把锁租出去一个有效期；看门狗在到期前替仍在用锁的线程续期，业务结束后必须停止续期。

i
类比

酒店房卡 30 分钟有效。住客还在房间里，前台每 10 分钟给他续一次卡；人退房后必须停止续卡。如果卡已经过期、房间分给了新住客，前台不能再把旧住客的卡续上——那会让两个人同时拥有同一个房间。

纯内存版只需要两个状态：owner 和 expireAtNanos。获取时如果锁空闲或租约已过期，就写入新 owner 与新的到期时间；释放时校验 owner，迟到的旧持有者不能释放新持有者的锁。所谓“看门狗”，就是一个守护线程按 lease/3 的间隔调用续期。

核心代码：获取、续期与释放都要校验

java · WatchdogDemo#Lease 与续期任务（节选）
// 租约 = owner + 到期时间；判断与写入必须在同一个临界区里完成
synchronized boolean tryAcquire(String candidate, long leaseMillis) {
    long now = System.nanoTime();
    if (owner == null || now >= expireAtNanos) {        // 空闲或已过期才能接管
        owner = candidate;
        expireAtNanos = now + TimeUnit.MILLISECONDS.toNanos(leaseMillis);
        return true;
    }
    return false;
}

// 看门狗每 lease/3 续期一次；owner 变了或租约已过期就返回 false，任务随即停止
synchronized boolean renew(String expected, long leaseMillis) {
    long now = System.nanoTime();
    if (!expected.equals(owner) || now >= expireAtNanos) {
        return false;                                    // 拒绝“过期后复活”
    }
    expireAtNanos = now + TimeUnit.MILLISECONDS.toNanos(leaseMillis);
    return true;
}

// 带 owner 校验的释放：A 迟到时不能把 B 已经拿到的锁删掉
synchronized boolean release(String expected) {
    if (expected.equals(owner)) {
        owner = null;
        return true;
    }
    return false;
}

// 释放前先停表，否则解锁后看门狗可能还在续期
if (renewer != null) {
    renewer.shutdownNow();
    awaitTermination(renewer);
}
lease.release("A");

4.2分段计数：把热点拆到多个 Cell

一句话：LongAdder 不追求“所有线程更新同一个变量”，而是让线程各自更新一个 Cell，读取时再把所有 Cell 加起来。

i
类比

超市有 32 个收银员，却只有一台总收银机：每个人都排队去按同一个按钮。分段计数相当于开 16 台收银机，每个人按自己的机器，最后把 16 台机器的金额相加。

实现只需要三件事：一个 Cell[] 数组、一个把线程映射到格子的规则、一个最后求和的 sum()。本例把 Cell 数量向上取到 2 的幂，用 threadId & (size - 1) 选格——同一线程总是命中同一格，不同线程尽量分散。

核心代码：选格与求和

java · StripedCounterDemo#StripedCounter（节选）
// 16→16、17→32：Cell 数向上取到 2 的幂，减一就是取模掩码
this.mask = size - 1;

void increment() {
    int index = (int) (Thread.currentThread().threadId() & mask); // 同一线程固定命中一格
    cells[index].increment();                                      // 每格独立 getAndAdd
}

long sum() {
    long total = 0;
    for (Cell cell : cells) {   // 逐格读取，没有全局锁
        total += cell.value;    // 并发时可能读到中间状态，不是原子快照
    }
    return total;
}

4.3分片 Map 锁：一把大锁拆成多把小锁

一句话：把 key 哈希到固定数量的分片，每个分片一把锁、一张表；不同分片的操作互不阻塞，锁的竞争范围从整张表缩小到一个分片。

i
类比

图书馆只有 1 个借阅台，所有读者排一队；改成 16 个借阅台、每人按书名首字母去对应窗口，队伍立刻变短。但如果所有人都借同一本热门书，还是只能挤在同一个窗口——分片救不了热点。

本例对比三种策略：global 用 1 把锁保护整张表；sharded 用 16 把锁、每把锁保护自己的 HashMap；hotkey 仍然分 16 片，但所有线程操作同一个 key，最终落到同一片。锁内忙等 200µs 模拟业务耗时，让串行与并行在总时长上体现出来。

核心代码：每个分片一把锁、一张表

java · ShardedMapDemo#runMode（节选）
int shardCount = mode == Mode.GLOBAL ? 1 : shards;
ReentrantLock[] locks = new ReentrantLock[shardCount];
List<Map<String, Integer>> maps = new ArrayList<>(shardCount);

// 每个分片：一把锁 + 一张自己的 HashMap（不是 16 把锁共用一张表）
for (int i = 0; i < shardCount; i++) {
    locks[i] = new ReentrantLock();
    maps.add(new HashMap<>());
}

int shard = Math.floorMod(key.hashCode(), shardCount);
locks[shard].lock();
try {
    spinMicros(workMicros);                 // 模拟业务耗时，让串行/并行可见
    maps.get(shard).merge(key, 1, Integer::sum);
} finally {
    active.decrementAndGet();               // 先退出计数，再 unlock
    locks[shard].unlock();
}

读法：全局锁下 8 个线程完全串行；16 分片下 8 个线程可以同时进入各自的临界区，maxConcurrent=8，耗时约 69ms；热点 key 模式所有操作落到同一分片，maxConcurrent 回到 1，耗时与全局锁相同。分片分布也不均匀：64 个 key 的哈希没有落到第 4 个分片（计数为 0），热点 key 固定落在第 13 个分片。

!
坑：分片锁必须“每片一张表”

最初所有分片共用同一张 HashMap，只按 key 配锁。不同分片仍会并发修改同一张表的扩容/链表结构，实测出现过 mapSize=63（应为 64）——锁只锁住了自己的 key，没有锁住表结构。修复方式是每个分片各持一张表，这也正是 ConcurrentHashMap 1.7 中 Segment 的形态：一把锁保护一张子表。测试因此加入了 5 轮重复运行，防止回归。

!
边界：分片数、热点与扩容

分片越多，理论并行度越高，但每片的内存、元数据和求和成本也越高；分片数通常取 2 的幂，便于用掩码定位。更关键的是热点：只要大量请求命中同一个 key，16 把锁就会退化成 1 把。真实系统需要先识别热点，再做 key 拆分、缓存或异步合并，而不是盲目加大分片数。

05边界与反例：把错误结果放在一起看

九个实验覆盖了机制的正反面。下面把最容易踩的边界集中成一张表，方便写代码前快速对照。

现象根因正确做法
两个线程各 new 一个 Object 去同步，仍然并发锁的是不同对象，监视器不是同一个共享同一个 private static final 锁对象
临界区里 sleep，另一个线程还是进不来sleep 不释放锁需要让出锁时用 wait() 或 Condition.await()
unlock 抛 IllegalMonitorStateException当前线程没有持有锁，或 unlock 次数多于 locklock/unlock 成对，unlock 放 finally
synchronized 等待中被中断，线程仍不退出monitorenter 不可中断，只置标记需要取消/超时用 lockInterruptibly() 或 tryLock(timeout)
非公平锁下某个线程很久拿不到锁释放者或其他线程持续插队对延迟敏感时用公平锁，并给等待设上限
并发 count++ 结果小于预期读改写三步可交错，后写覆盖先写锁、AtomicLong 或 LongAdder，按竞争程度选择
LongAdder.sum() 在并发时偏小sum 不是原子快照，Cell 仍在更新用于最终统计；需要瞬时精确值改用 AtomicLong
租约锁下两个线程同时进入临界区租约到期后无人续期，锁被新持有者接管长业务开启看门狗；释放前停止续期
看门狗把已经被别人接管的锁续上续期前没有校验 owner 或到期时间renew 必须校验 owner，过期就放弃
分片数加到 16，仍有大量线程排队所有请求命中同一个热点 key，落到同一分片先治理热点（拆 key、缓存、异步合并），分片数救不了热点
按 key 分了锁，Map 仍偶发少 key多个分片共用同一张 HashMap，表结构仍被并发修改每个分片各持一张表，锁保护自己的子表
手写分段计数在单 Cell 时比 AtomicLong 慢多一层数组与 threadId 寻址，且没有 JIT 内建优化分段只在确实分散到多个 Cell 时才有收益
应用刚启动后第一次吞吐对比明显偏慢JIT 尚未完成 C2 编译，预热轮不足每种写法先跑 2 轮预热，再取多轮中位数

锁能保证

  • 同一把锁上的互斥
  • unlock/lock 或 monitorexit/monitorenter 之间的可见性
  • 同一线程的可重入
  • 可选的公平、可中断、超时（ReentrantLock）

锁不能保证

  • 不同锁对象之间的互斥
  • 线程调度的公平（公平锁也只管队列顺序）
  • 不死锁：加锁顺序不一致仍会成环
  • 跨服务、跨数据库的事务一致性

选型速查

需求首选理由
简单临界区，无超时/中断需求synchronized语法短，自动释放，JVM 持续优化
需要 tryLock、超时、可中断、公平或 ConditionReentrantLock能力更全，但必须手动 unlock
低竞争计数且需要返回值AtomicLongCAS 无锁，读写都精确
高竞争计数/求和，只关心最终值LongAdder分段累加，减少 CAS 冲突
锁要跨进程/跨服务，且持有时间不确定租约锁 + 看门狗到期可接管，续期保活；释放前必须停止续期
单表并发写严重且 key 分布均匀分片锁（每片一锁一表）把锁范围缩小到一个分片；热点 key 仍需单独治理
临界区里要同时改多个变量锁原子类只能保护单个变量
多把锁的嵌套全局固定顺序 + tryLock 超时从规则上消除等待环，并保留恢复能力
