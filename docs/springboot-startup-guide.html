02从注解讲起：你写的每个注解，点亮的是哪个类

Spring Boot 没有魔法。它做的只有两件事：读你写的注解，然后调用处理这个注解的类。 所以「启动原理」的正确起点不是 run() 的九个阶段，而是这张 「注解 → 类 → 容器里多了什么」对照表。本章的每一个数字都由反射和类路径现场算出来， 接口共 7 个，全部可重复执行。

≈

类比：墙上的开关面板 注解是家装完留在墙面上的开关面板——你只看得见面板上的字（@EnableXxx）， 看不见墙里的走线。@EnableScheduling 后面接的是 SchedulingConfiguration，@ConfigurationProperties 后面接的是 ConfigurationPropertiesBindingPostProcessor。 学启动原理，本质就是把「按哪个开关、哪台电器会转」这张表抄下来并验证它。

2.2 把 @SpringBootApplication 剖开：12 次出现，9 个类型

「@SpringBootApplication = 三合一」这句人人都背，但很少有人数过它到底套了几层。 本模块用两条互不依赖的路径同时看：JDK 反射递归（完全不碰 Spring）和 Spring 的 MergedAnnotations。下面这棵树是递归打印出来的，缩进一层就是深一层元注解。

java · annotations/AnnotationTreeService.java（递归核心，节选）
private void walk(Annotation present, int depth, String declaredOn, List<TreeRow> rows, Set<String> path) {
    Class<? extends Annotation> annType = present.annotationType();
    if (depth > MAX_DEPTH || !path.add(annType.getName())) {
        return;                       // 同一条链上重复 = 注解互相引用，截断
    }
    rows.add(new TreeRow(depth, annType.getName(), declaredOn, attributesOf(present)));
    for (Annotation meta : annType.getAnnotations()) {
        // 跳过 @Target/@Retention/@Documented：它们是注解的"定义元信息"，不承载装配语义，
        // 留着会把树读成一堵墙，读者要找的 @Import/@Conditional 会被埋掉
        if (meta.annotationType().getName().startsWith("java.lang.annotation")) {
            continue;
        }
        walk(meta, depth + 1, annType.getName(), rows, path);
    }
    path.remove(annType.getName());   // 回溯：允许同一个元注解出现在另一条分支上
}

读这份数字的三个抓手：

  • 44 个候选 → 20 个进容器。剩下的被条件挡掉了，这正是 场景 3 条件报告存在意义； 而 27 个「@Import 导入的配置类」是别的配置类通过 @Import 拉进来的， 它们不在候选名单里。
  • 自动配置只贡献了 20 + 一部分 @Bean 方法：90 个 @Bean 产物里绝大多数来自自动配置类的方法。所以「Bean 定义从 6 跳到 191」不是玄学，是这两桶。
  • 那 1 个「其它」是主类自己。SpringApplication 拿到你的主类后 直接 register，走的是最朴素的注册路径——它不在扫描结果里，也不是 @Import。
≡

一眼认出 Bean 是怎么进来的 扫描产物 = 首字母小写短名（featureEnableDemoConfig）； @Import / 自动配置导入 = 类全限定名当 Bean 名 （com.example.demo…StartupFeatureBasicConfig）； @Bean 方法 = 方法名（startupFeatureApiBasic）。 以后在 /actuator/beans 或日志里看到一长串 FQN，就知道它是被"导入"的而不是被"扫"的。

2.7 自己写一个 @EnableXxx：@Import + 一个选择器就是全部魔法

把前面所有零件合起来用一次：@EnableStartupFeature 是本模块手写的注解， 成员 mode 决定导入哪个配置类。javap 出来的 @EnableConfigurationProperties 和 @EnableAutoConfiguration 同样是「一个 @Import」，形状完全一致。

java · annotations/feature/EnableStartupFeature.java + StartupFeatureSelector.java（节选）
@Target(ElementType.TYPE)
@Retention(RetentionPolicy.RUNTIME)      // 丢了 RUNTIME，Spring 在运行期根本读不到这个注解
@Import(StartupFeatureSelector.class)    // ← @EnableXxx 的全部机制就这一行
public @interface EnableStartupFeature {
    String mode() default "basic";
}

public class StartupFeatureSelector implements ImportSelector {
    @Override
    public String[] selectImports(AnnotationMetadata importingClassMetadata) {
        // importingClassMetadata 是"标了 @EnableStartupFeature 的那个类"的元数据，
        // 靠它才能把注解上的 mode 取出来——这是 @EnableXxx 能带参数的原因
        Map<String, Object> attrs = importingClassMetadata
                .getAnnotationAttributes(EnableStartupFeature.class.getName());
        String mode = (String) attrs.getOrDefault("mode", "basic");
        String[] imports = switch (mode) {
            // 返回"类名字符串"而不是 Class：延迟到后续阶段才加载，可选依赖才敢这么写
            case "full"  -> new String[]{StartupFeatureFullConfig.class.getName()};
            default      -> new String[]{StartupFeatureBasicConfig.class.getName()};
        };
        HISTORY.add(new Resolution(importingClassMetadata.getClassName(), mode, List.of(imports)));
        return imports;
    }
}

03心智模型

i

一句话纠正最大的误解 很多人以为 run() 就是「创建容器」，Bean 定义在启动前就都排好了。 实测：contextLoaded 时只有 6 个 Bean 定义，refresh 完成后是 191 个—— 自动配置走 DeferredImportSelector，要等 refresh 期间才展开。

≈

类比：毛坯房交接 starting 是集合点名，environmentPrepared 是把水电清单（配置）核对完， contextPrepared 是拿到房子（容器实例，空的），contextLoaded 是图纸进场（Bean 定义）， refresh() 才是真正施工，started 是验收、ready 是交钥匙可以住人。

误解实测事实为什么容易记错
启动日志的第一行是 starting 第一行是 [environmentPrepared]，starting 阶段根本没有日志 日志系统（LoggingSystem）自己在 environmentPrepared 里才初始化
Bean 定义在 refresh 前就齐了 6 个 → 191 个 自动配置是延迟导入选择器，refresh 期间才解析
条件报告要靠 --debug 打开 每次启动都会记录，--debug 只决定打不打印 不打印 ≠ 没记录；本模块的接口就是直接读内存里那份报告
排除一个自动配置只影响它自己 实测第二个子应用直接启动失败 自动配置之间是有依赖图的集合，不是孤立开关

6.2 让条件自己解释为什么

普通 Condition 只回答 true/false；继承 SpringBootCondition 后， 框架会把 getMatchOutcome 返回的「布尔 + 一句话」一起记进报告。 排障时这句话就是省掉半小时的关键。

java · autoconfig/FeatureColorCondition.java
public class FeatureColorCondition extends SpringBootCondition {

    static final String PROPERTY = "demo.startup.autoconfig.feature-color";

    @Override
    public ConditionOutcome getMatchOutcome(ConditionContext context, AnnotatedTypeMetadata metadata) {
        // context.getEnvironment() 是条件阶段唯一安全的取值通道：
        // 此时属性源已全部就位（environmentPrepared 早已完成）
        String value = context.getEnvironment().getProperty(PROPERTY);
        // null 要显式处理：getProperty 缺失时返回 null，直接 equals 会 NPE 炸掉启动
        boolean matched = value != null && value.toLowerCase().contains("green");
        String explain = "属性 " + PROPERTY + " 当前值=\"" + value + "\"，判定规则=值包含 green";
        return matched ? ConditionOutcome.match(explain) : ConditionOutcome.noMatch(explain);
    }
}

@Component
public class LifecycleTraceProcessor implements BeanPostProcessor {

    @Override
    public Object postProcessAfterInitialization(Object bean, String beanName) throws BeansException {
        if (!(bean instanceof LifecycleDemoBean target)) {
            return bean;   // 非演示 Bean 原样返回：否则框架 Bean 全被包成代理
        }
        record(key, "bpp-after", "返回 JDK 动态代理替换原对象");
        return Proxy.newProxyInstance(bean.getClass().getClassLoader(),
                new Class<?>[] { LifecycleDemoApi.class },      // JDK 代理只认接口
                (proxyObject, method, args) -> {
                    record(key, "proxy-invoke",
                            "调用落在代理上（" + proxyObject.getClass().getSimpleName() + "）");
                    return method.invoke(target, args);        // 反射转发给真实对象
                });
    }
}
