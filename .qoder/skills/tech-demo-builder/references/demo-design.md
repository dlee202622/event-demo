# 案例矩阵：从技术主题到可观察场景

## 为什么要先写矩阵

“Redis 的 demo”不是一个案例，而是一组互相印证的实验。矩阵迫使每个场景回答三件事：

1. 它在证明什么机制？
2. 跑完之后看哪个数字/输出？
3. 去掉某个保护会发生什么？

如果答不上来，这个场景就不该写。

## 四类场景

### 核心场景

解释机制本身。每个核心场景至少包含：

- 一次正常路径
- 一次“看一眼底层结构”（Redis 的 `TYPE`/`TTL`/原始值、数据库行、队列积压）
- 一句“什么时候用它、什么时候别用”

例：限流的单次判定 + `/{algorithm}/state` 查看 ZSet/Hash 结构。

### 对比场景

同一组参数下让两种实现同台，输出必须并排展示。

例：同一 `limit=5, window=10s` 下六种限流算法各发 15 次，对比 `allowed`、`firstDeniedAtMillis`。
对比要控制变量：同样的 key 隔离、同样的请求间隔、并行执行避免总耗时叠加。

### 边界场景

把参数推到临界点，展示“看起来正确”的实现如何失效。

例：窗口结束前 85% 发满一批，跨过边界再发一批。固定窗口 5/5 全放行，滑动窗口 5/0 拦截。
边界实验必须自己计算时间点，不能靠 `sleep` 猜；允许误差但结论要稳定。

### 故障 / 竞态场景

主动移除保护或制造时序，让错误稳定出现。

例：

- 关掉看门狗，业务执行时间 > 锁 TTL，B 进入临界区，`overlap=true`
- 不加锁的读-改-写计数，20 线程 × 20 次，实际值明显小于 400
- 读线程在删除后回填旧值，延迟双删前缓存为脏，二次删除后回源

竞态实验要有明确的时序注释和可复现的等待点，不能依赖“运气”。

## 可观察性规则

1. **一条命令**：每个场景都要有可直接复制的 curl/命令。
2. **数字优先**：返回里至少有一个可比较的数字（放行数、耗时、TTL、误差、丢失量）。
3. **结构可见**：能查看底层存储形态时一定提供（Redis 类型、数据库行、pending 列表）。
4. **成对出现**：保护开/关、算法 A/B、边界前/后，必须能并排对照。
5. **重复稳定**：连续跑两次结果一致；时间相关实验给出容差范围。
6. **失败有语义**：错误响应说明原因和可选值，不用 500 掩盖参数问题。

## 验收清单

- [ ] 核心 / 对比 / 边界 / 故障四类至少各一个
- [ ] 每个场景有触发命令、观察字段、预期数量级
- [ ] 对比场景控制变量，边界场景自己算时间
- [ ] 竞态场景可稳定复现，且注释写清时序
- [ ] 至少有一个“反例”：去掉保护后结果明显错误
- [ ] 场景数量控制在 4–8 个，宁少勿滥
